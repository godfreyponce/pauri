# Pauri Remembers Its Chats; Cmd+K Opens a Plain List Implementation Plan (refs #20)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Pauri records the ID of every chat it asks in, and Cmd+K opens a plain popover list of those chats (title and date, newest first); a click reopens one with its old turns and makes it the last chat.

**Architecture:** Task 1 is the Codex side, in `CodexClient` and `CodexProtocol`: a remembered ID list in `UserDefaults`, `history()` (pages `thread/list` and keeps only remembered IDs), and `resume(_:)` (switches the warm process to another thread). Task 2 is the app side: `Chat.open(_:)`, a new `HistoryList.swift` view, a Cmd+K button with a popover in `PanelView`'s header, one live test, the hand checks, and the full check.

**Tech Stack:** Swift 6, SwiftPM, SwiftUI (macOS 14), Swift Testing. No new dependency.

**Spec:** issue #20; parent #19 (decisions 5 to 9); sibling #22 (restyles this list into variant C of `design-directions/issue-21.html` and adds search and delete). Protocol types checked against `codex app-server generate-ts` from codex-cli 0.169.0 (`v2/ThreadListParams.ts`, `v2/ThreadListResponse.ts`, `v2/Thread.ts`, `v2/ThreadResumeParams.ts`).

## Data flow

```text
Chat.send --> CodexClient.ask --> codex app-server: thread/start, turn/start
                    |
                    +--> UserDefaults "lastThreadID"
                    +--> UserDefaults "threadIDs" (new)

Cmd+K --> PanelView header button (changed) --> HistoryList (new)
            --> Chat.history (new) --> CodexClient.history (new)
                  +--> codex app-server: thread/list, every page (new)
                  +--> UserDefaults "threadIDs" (new)  == filter ==> rows

HistoryList row click --> Chat.open (new) --> CodexClient.resume (new)
                            +--> codex app-server: thread/resume (changed: also called after launch)
                            +--> UserDefaults "lastThreadID" (changed: also written here)
```

## What exists today (read 2026-11-14)

- `CodexClient` keeps one thread ID in memory and saves it as `lastThreadID` in `UserDefaults` after each `turn/start` (`CodexClient.swift:108-110`), because Codex writes a thread to disk only at its first turn. `launch()` resumes that ID with `thread/resume` and keeps the turns in `restoredExchanges` (`:211-224`). `forgetThread()` clears it (Cmd+N).
- `ThreadResumeResult` (`CodexProtocol.swift:337-370`) turns a resume reply into `[Exchange]`.
- `Chat.showRestoredTurns()` inserts the launch thread's turns once and loads the model picker (`Chat.swift:74-80`). `Chat.newChat()` resets the chat state (`:82-90`).
- `PanelView`'s header is an `HStack` with the pencil (Cmd+N) and the gear, whose settings popover already works in this non-activating panel (`PanelView.swift:50-62`). Esc on the panel hides it (`FloatingPanel.cancelOperation`); in a popover, Esc closes only the popover.

## What the probes showed (codex-cli 0.169.0, on the owner's Mac, 2026-11-14)

- **`sourceKinds: ["appServer"]` returns zero threads.** Codex records app-server threads, Pauri's and T3 Code's, with source `vscode`. Leave `sourceKinds` out; the default (interactive sources) includes them.
- **`thread/list` caps a page at 100.** `limit: 1000` gave the same 4 pages for 356 threads as `limit: 100`. Paging every page took about 0.5 s.
- **`originator` is the `clientInfo.name`** (`"pauri"` for Pauri, `"T3 Code"` for T3 Code). 156 threads carry `"pauri"`, almost all from the live tests. The remembered ID list is the filter, as the ticket says; `originator` is not used, so test threads never show.
- **`name` is null for every Pauri thread.** Codex does not name app-server threads. The title is `name` when set, otherwise `preview` (the first user message).
- **`thread/resume` works on a thread already loaded in the same process** (A, B, A again: each returned its turns).
- **`thread/resume` of a missing thread is an error reply** (`-32600`, "no rollout found for thread id ..."), and the process keeps working: the next resume in the same process succeeded.

## Gate 1 decisions (owner: change any of these before go)

1. **`thread/list`, not `thread/read` per ID.** The ticket's filter test is written against a `thread/list` reply, and one paged call finds every remembered chat in about 0.5 s. `thread/read` per ID would cost one request per Pauri chat and would need a second error path for missing threads.
2. **Pauri records the thread on every question, not only on threads it starts.** One idempotent write next to the `lastThreadID` write. The effect: the last chat from before this build joins the list the first time you ask in it again. Chats from before this build that you do not continue never appear, and nothing guesses by working folder. Alternative: a flag that records only threads this build started, so the old last chat never appears.
3. **Newest first means last updated** (`sortKey: "updated_at"`), and the date shown is the last update. A chat you reopen and continue moves to the top. Alternative: `created_at`, Codex's default.
4. **The list is a popover from a clock button in the header**, at the left of the pencil, with tooltip "Past chats (⌘K)". The popover is the pattern the gear already uses, and Esc or a click outside closes it without hiding the panel. No variant page: the ticket says the look is plain on purpose, and #22 builds the look you already picked in `design-directions/issue-21.html` (variant C, a palette over the whole panel with a search icon).
5. **No paging test.** The live test's chats are the newest threads, so they are on page 1. Paging past page 1 is exercised only on a Mac with more than 100 newer threads than the chat. A page-size parameter to force it in a test would be configurability for the test only.

## Review Focus

1. **A question sent while a reopen is in flight.** Expected: the send is refused until the old turns show, so no answer streams into a chat that is about to be replaced. Task 2 guards `send` with `isOpening`; hand check 6.
2. **The reopen fails** (the chat's session file was deleted outside Pauri). Expected: the current chat stays, the notice shows the error, and the next question still goes to the current chat. Task 1's `resume` puts the old thread ID back; the live test in Task 2 resumes a bad ID and then asks a follow-up.
3. **A remembered chat that Codex no longer lists.** Expected: it is left out, with no error. Task 1's filter test keeps a remembered ID that is not in the reply.
4. **Cmd+K during an answer, a handoff, or the start at launch.** Expected: the list opens but its rows are disabled. Task 2 disables rows on `!chat.canStartNewChat`; hand check 6.
5. **The first launch of this build.** Expected: the list says "No chats yet." until a chat gets its first answer, and the hotkey still brings back the old last chat. Hand checks 1 and 4.

- [ ] **Step 3: Add `ThreadListResult` and `HistoryEntry` to `CodexProtocol.swift`**

`ThreadListResult` decodes `data` as a private `[Thread]` (`id: String`, `name: String?`, `preview: String`, `updatedAt: Int`, seconds since 1970) and `nextCursor: String?`. `entries(remembered:)` keeps the reply's order. Title: `name` when it is non-nil and non-empty, otherwise `preview`.

- [ ] **Step 4: Add the remembered list, `history()`, and `resume(_:)` to `CodexClient.swift`**

- Key: `private static let historyKey = "threadIDs"`, a `[String]` in `defaults`, oldest first.
- `remember(_:)` appends when the ID is not in the list. `forgetThread()` does not touch the list.
- In `ask`, call `remember(threadID)` right after the existing `defaults.set(threadID, forKey: Self.threadKey)` (decision 2).
- `history()`: `try await start()`, then call `thread/list` with `["limit": 100, "sortKey": "updated_at"]`, plus `"cursor"` when there is one, until `nextCursor` is nil. Collect `entries(remembered: Set(rememberedThreadIDs))` from each page. One comment on the params carries the why: `// No sourceKinds: Codex records app-server threads as "vscode", so ["appServer"] matches none. 100 is the server's page cap (codex-cli 0.169.0).`
- `resume(_:)`: `try await start()`; keep `let previous = threadID`; set `threadID = threadID-to-open` **before** the send (the same reason as the comment at `:212-213`: the usage notification can arrive before the reply); send `thread/resume` with `Self.resumeParams(_)`; on success, save the ID under `Self.threadKey` and return `ThreadResumeResult.exchanges`; on any error, set `threadID = previous` and rethrow.
