# Show the Panel After an Update Relaunch Implementation Plan (refs #32)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** When Pauri relaunches after a one-click update, it shows its panel without a shortcut press; every other launch still starts hidden.

**Architecture:** The old Pauri, just before Sparkle relaunches it, sets one user default (`PauriShowPanelAfterUpdate = true`) in the `SPUUpdaterDelegate` hook `updaterWillRelaunchApplication(_:)`. The new Pauri, at the end of `applicationDidFinishLaunching`, reads the flag, removes it, and calls `panel.show()` if it was set. The ticket's pointer, `showUpdateInstalledAndRelaunched` (`Sources/Pauri/Updater.swift:79`), is the wrong hook and stays as it is: Sparkle calls it only in the *old* process, and only if that process is still alive (`SPUUserDriver.h`: "This will only be invoked if the updater process is still alive, which is typically not the case"). The new process cannot tell the update apart from an ordinary `open` by itself: Sparkle relaunches with a plain `[[NSWorkspace sharedWorkspace] openURL:]` (`InstallerProgressAppController.m:408`), with no argument and no Sparkle default written at install time (`SUConstants.m`). So the old process must leave the note (decision D1).

**Tech Stack:** Swift 6, AppKit, Sparkle 2.10.1 (`SPUUpdaterDelegate`, `NS_SWIFT_UI_ACTOR`, so the hook runs on the main actor), `UserDefaults`, Swift Testing.

**Spec:** issue #32. Builds on #28 (`docs/superpowers/plans/2026-11-16-issue-28.md`: the `Updater` class and the test-feed hand check this plan reuses).

## Data flow

```text
OLD Pauri (version N), after the header-button click
  Sparkle SPUCoreBasedUpdateDriver
    --updaterWillRelaunchApplication--> Updater (changed)
    --writes--> UserDefaults io.github.godfreyponce.pauri : PauriShowPanelAfterUpdate = true (new)
  Sparkle installer --replaces--> Pauri.app --NSWorkspace openURL--> NEW Pauri

NEW Pauri (version N+1), any launch
  AppDelegate.applicationDidFinishLaunching (changed)
    --reads, then removes--> UserDefaults : PauriShowPanelAfterUpdate (new)
    |
    +-- was true  --> PanelController.show()
    +-- absent    --> panel stays hidden (as today)
```

## Decisions for gate 1

- **D1. The flag is written by the old process, so it works only when the old version has the fix too.** The first public release with the fix (call it 0.1.2) does *not* show the panel when a copy updates to it from 0.1.1: 0.1.1 writes no flag. The first public update that shows the panel is 0.1.2 to 0.1.3. Pick: accept this. Analogy: a note on the fridge only helps if someone was there to write it before leaving. Alternative the owner may prefer: also show the panel on the first launch of a new `CFBundleShortVersionString` (store the last launched version). That covers 0.1.1 to 0.1.2, but it also shows the panel after a `brew upgrade` or a hand-copied install, at whatever launch comes next (login included), and it cannot tell a first install from an update when no version was stored. That breaks "an ordinary launch still starts hidden" in those cases, so it is not the pick.
- **D2. The proof uses the local test feed, no public release.** Two local builds, both with the fix, as in #28's hand check: build N at 0.1.0 pointed at `PauriTestFeedURL`, and N+1 stamped 0.1.2 by `./scripts/build-app.sh --release 0.1.2` served from `build/test-feed/`. This answers the Done-when question: yes, a test feed proves it without a public release. The public proof is 0.1.2 to 0.1.3, whenever the owner ships 0.1.3; this ticket does not wait for it.
- **D3. The flag is cleared at every launch, read or not.** If the relaunch fails and the owner opens Pauri by hand later, that one launch shows the panel. Pick: accept it; it happens once and only after a click on the update button.
- **D4. No README change.** README lines 33 and 52 already say one click "installs it and restarts Pauri", which is now what the user sees.

## Review Focus

- **An ordinary launch after a past update.** The flag must not survive the launch that read it; a later `open` or login launch starts hidden. Pinned by `relaunchFlagShowsOnce`.
- **A launch with no update ever.** No flag means hidden. Pinned by `ordinaryLaunchStaysHidden`.
- **Install on quit (no relaunch).** Sparkle calls `updaterWillRelaunchApplication` only when it relaunches (`SPUCoreBasedUpdateDriver.m:332`, `if (relaunch)`), so no flag is set. Pauri never asks for install on quit today; no test, noted for the reader.
- **Focus.** The relaunched panel is shown with `PanelController.show()`, the same call the shortcut uses (no `NSApp.activate`), so it takes keys the same way. Hand check H5.
- **Failed install.** `showUpdaterError` paths run before the relaunch hook, so no flag. Covered by D3 for the late-failure case.
