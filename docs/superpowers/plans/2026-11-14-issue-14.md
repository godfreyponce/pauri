# Stop an Answer from the Send Orb's Square Implementation Plan (refs #14)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A click on the send orb's square while an answer streams stops the turn in `codex app-server`, keeps the text so far, and turns the orb back into the arrow.

**Architecture:** `CodexClient` keeps the id of the turn that `turn/start` returns, and a new `stopAnswer()` sends `turn/interrupt` with that id. Codex then ends the turn with `turn/completed`, status `"interrupted"`, which Pauri now reads as a clean end, so the stream finishes without an error and `Chat`'s existing end-of-turn code runs. `PanelView` routes the orb's click to `Chat.stop()` while answering and to `submit()` otherwise.

**Tech Stack:** Swift 6, SwiftUI, Swift Testing. No new dependency.

**Spec:** issue #14. No design spec. Builds on #10 (the square, `docs/superpowers/plans/2026-11-13-issue-10.md`) and #3 (the live tests).

## Data flow

No data-flow change: the stop is one more JSON-RPC request (`turn/interrupt`) on the existing stdin pipe to the same `codex app-server` child; no file, folder, process, or output starts or stops being read or written.

## What the probe found (2026-11-14, codex-cli 0.169.0, this Mac)

The planning session ran a Python probe against a real `codex app-server` (ephemeral thread, a few tokens):

- `turn/start` replies `{"turn": {"id": "<turn id>", "status": "inProgress", ...}}`. That reply is the only place Pauri needs the id from.
- `turn/interrupt` with params `{"threadId": ..., "turnId": ...}` (type `TurnInterruptParams` in `codex app-server generate-ts`) replies `{}` at once.
- Right after, Codex sends `turn/completed` with `"status": "interrupted", "error": null`. No `error` notification comes.
- The next `turn/start` on the same thread answers as normal ("hi").

Today `CodexNotification` maps any status other than `"completed"` to `.turnCompleted(errorMessage: "Codex ended the answer (interrupted).")`, so without a change a stop would show that line as the notice.

## Gate 1 decisions (owner: change any of these before go)

1. **A stopped answer ends quietly.** No notice under the chat; the partial text is the record. `turn/completed` with status `"interrupted"` maps to `.turnCompleted(errorMessage: nil)` for every turn, because only Pauri talks to its own app-server child, so only Pauri can interrupt a turn. Alternative: a short "Stopped." notice.
2. **A click before the turn has an id still stops it.** The square shows from the moment of send, but the turn id arrives only with the `turn/start` reply (seconds later at launch, while Codex starts). Such a click is remembered, and `ask` interrupts the turn as soon as its id arrives. The question still reaches Codex and stays in its thread, matching what the panel shows. Alternative: ignore the click until the id is known (then a click during the start does nothing, the bug this ticket fixes).
3. **The orb's tooltip and VoiceOver label say "Stop" while answering**, "Send" otherwise. Today they say "Send" on the square.

No visual rule: the square already exists (#10); only its click and its label change, so no HTML variants.

## Global Constraints

- Stop the turn through `codex app-server` itself (`turn/interrupt`), so Codex stops working too; do not only stop reading the stream (ticket constraint).
- Enter in the text field must not stop an answer: `TextField.onSubmit` stays `submit`.
- Public repo: no env values, credentials, or owner personal data in code, tests, or commits.

## Review Focus

1. **Stop while an approval card shows.** The card goes away and the orb returns to the arrow (the existing end-of-stream `approvals = []` covers it). Hand check in Step 9.
2. **Stop during the launch start.** Covered by the live test `liveStopBeforeTheTurnStartsEndsTheAnswer`.
3. **Two clicks on the square.** The second `turn/interrupt` gets an error reply or `{}`; either is ignored (`try?`). No notice, no crash.
4. **A command step still running at the stop** ends as "(failed)" through the existing `endedWithTurn`. Accepted for now; if it reads wrong in the hand check, file a new issue, do not fix it here.
5. **Stop, then the next question.** Covered by `liveStopKeepsTheTextAndTheNextQuestionAnswers` and the hand check.

- [ ] **Step 7: Implement the stop in `CodexClient`**

- `TurnStartResult` in `CodexProtocol.swift`: decodes `{"turn": {"id": String}}`, the shape of `ThreadStartResult`.
- Two new private properties: `turn: (threadID: String, id: String)?`, the turn `startTurn` started last, and `stopRequested: Bool`, set by a stop that came before the turn's id.
- `startTurn` decodes the `turn/start` reply as `TurnStartResult` and sets `turn` (for the handoff fork too; harmless, a stop cannot be clicked during a handoff).
- `ask(_:)` sets `turn = nil` and `stopRequested = false` synchronously, before its `Task`. Inside the `Task`, right after `try await startTurn(...)`: `if stopRequested { stopAnswer() }`. `writeHandoff` never reads `stopRequested`.
- `func stopAnswer()`: sets `stopRequested = true`; if `turn` is set, sends `turn/interrupt` with `["threadId": turn.threadID, "turnId": turn.id]` through the existing `send` in a `Task`, with the result discarded and errors ignored (`_ = try? await`): the reply is `{}`, and an error only means the turn had already ended.

Run: `PAURI_LIVE=1 ./scripts/test.sh --filter liveStop`
Expected: both live tests pass.
