# Tool Steps and Approval Cards Implementation Plan (refs #5)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Codex can act on the Mac. Reads run with no prompt. A write or any other command shows an approval card (Allow, Deny, Allow for this chat). Each step shows as one small gray line that expands to show the command and its output.

**Architecture:** Threads start and resume with `sandbox: "read-only"` and `approvalPolicy: "on-request"` (the probe below shows that this policy gives the split). `CodexProtocol.swift` learns to read `item/started` and `item/completed` for `commandExecution` and `fileChange` items, and the two `item/*/requestApproval` server requests. `CodexClient.ask` streams `TurnEvent`s (text, step, approval) instead of plain text, and `CodexClient.decide` writes the reply. `Chat` keeps the steps on each exchange, a queue of open approvals, and the "allow for this chat" flag, which "New chat" clears. Two new views, `ToolStepRow` and `ApprovalCard`, show them in the shape the owner picks from a 4-variant page.

**Tech Stack:** Swift 6.2 (Command Line Tools), SwiftPM, SwiftUI (macOS 14), Swift Testing. One static HTML file with inline CSS and JS. Codex CLI 0.167.2 app-server protocol (types from `codex app-server generate-ts`).

**Spec:** `docs/spec.md` decisions 1, 9, 13; issue #5.

## Data flow

```text
PanelView.swift (changed)
  |  ToolStepRow.swift (new): one gray line per step, click -> command + output
  |  ApprovalCard.swift (new): Allow | Deny | Allow for this chat
  v
Chat.swift (changed)
  |  exchanges[i].steps, approvals queue, allow-for-this-chat flag
  |  Chat.decide(...) --> CodexClient.decide(request, .accept | .decline)
  ^
  |  TurnEvent: .text | .step | .approval   (changed: was String)
CodexClient.swift (changed)
  |  stdin -->  thread/start, thread/resume: sandbox "read-only",
  |             approvalPolicy "on-request"            (changed: was "never")
  |  stdin -->  {"id": <server id>, "result": {"decision": "accept"|"decline"}}  (new)
  |  stdout <-- item/started, item/completed (commandExecution, fileChange)    (new: read, were ignored)
  |  stdout <-- item/commandExecution/requestApproval,
  |             item/fileChange/requestApproval        (new: answered, were refused)
  v
codex app-server
  |  reads: run inside the read-only sandbox, no request
  |  writes and other commands: run only after "accept"  (new)
  v
files and processes on the Mac
```

Step lines stay in `Chat` and the view. Nothing in the send path reads them, so they never go back to the model.

## What the probe found (2026-11-13, codex-cli 0.167.2, this Mac)

A throwaway Python client (scratchpad, not in the repo) started `codex app-server`, opened an ephemeral thread with `sandbox: "read-only"`, and asked three things: count the Swift files, write a file with a shell command, write a file with apply_patch.

- **`approvalPolicy: "untrusted"` is wrong for this ticket.** It asked for approval on the read `rg --files --hidden -g '!.git' -g '*.swift' | wc -l` (commandActions: one `listFiles`). Done-when 1 would fail.
- **`approvalPolicy: "on-request"` gives the split.** The count ran with no request (`status: "completed"`, `aggregatedOutput: "      17\n"`). The shell write sent `item/commandExecution/requestApproval` with `reason: "Allow creating the requested out.txt file outside the read-only sandbox?"`. The patch write sent `item/fileChange/requestApproval` (`reason: null`, no paths: the paths are on the `fileChange` item from `item/started`, which came first).
- **`decline`** ended the item with `status: "declined"`, nothing was written, and the turn went on to `turn/completed` with `status: "completed"`. **`accept`** ran the command outside the sandbox and the file was written.
- **Codex's own `acceptForSession` does not stop the cards.** After `acceptForSession` on one shell write, a second, different shell write in the same thread asked again. `availableDecisions` in the request listed only `accept`, `acceptWithExecpolicyAmendment`, and `cancel`, but `decline` and `acceptForSession` were still accepted.
- Every `item/started` for a step came before its approval request, and `serverRequest/resolved` followed each reply.
- Real lines to use as test fixtures (ids shortened):

## Gate 1 decisions (owner: change any of these before go)

1. **Policy: `read-only` sandbox plus `approvalPolicy: "on-request"`** on both `thread/start` and `thread/resume` (probe above). Under this policy, Codex decides what counts as a read: anything that can run inside the read-only sandbox runs with no card. The sandbox also blocks network access. That matches the ticket's "reads means what Codex's read-only sandbox and approval policy treat as safe".
2. **"Allow for this chat" lives in Pauri, not in Codex.** Codex's `acceptForSession` covers only the same command (probe). So Pauri sends `accept` for the click and then answers every later request in that chat with `accept` itself, with no card. "New chat" clears the flag. A relaunch of Pauri also clears it, so the resumed chat asks again (the flag is only in memory). Pauri never sends `acceptForSession` or `acceptWithExecpolicyAmendment`: the amendment saves a permanent rule in Codex's config, past this chat.
3. **Deny sends `decline`, not `cancel`.** `decline` tells Codex no and the turn goes on (done-when 4). `cancel` would end the turn.
4. **Steps sit above the answer text in each exchange, in arrival order. They do not interleave with it.** When Codex writes a short message before a tool call ("I'll count them.") and then the answer, the two texts still join as they do today. If you want steps placed between the text parts, say so now: it changes `Exchange` from two strings into a list of parts, and the restore code for old chats changes with it.
5. **One line per Codex item, labeled from its `commandActions`:**
   - all `read` actions: one file gives `Read Package.swift` (the action's `name`), more gives `Read 2 files` (distinct `path` values);
   - all `listFiles`: `Listed files`;
   - all `search`: one action with a query gives `Searched for CodexClient`, otherwise `Searched files`;
   - anything else: one action gives ``Ran `git status` `` (the action's `command`), more gives `Ran 3 commands`, no actions gives ``Ran `<item command>` ``;
   - `fileChange`: one change gives `Created out.txt`, `Edited out.txt`, or `Deleted out.txt` (by `kind.type`, last path component); more gives `Changed 2 files`.
   A `declined` step gets ` (denied)` after its label, and a `failed` step gets ` (failed)`. Expanded, a command step shows the item's `command` exactly as Codex ran it (with the `/bin/zsh -lc` wrapper) and its `aggregatedOutput`. A file step shows the paths and their diffs.
6. **Old chats restored after a relaunch show no step lines.** Only text comes back, as today. The steps were UI-only, and `thread/resume` replays them as items that the restore code skips.
7. **The visual rule applies:** 4 variants on one page, `design-directions/issue-5.html` (AGENTS.md `# Visual rule`). The build stops after Task 1 for your pick. **References, pick 2–3 (or send your own):** (a) the Codex CLI's own approval prompt (run `codex` in Terminal and ask it to write a file); (b) the gray, collapsible "Ran a command" lines in the ChatGPT or Claude macOS app; (c) Pauri's current panel and `design-directions/issue-10.html`. The page takes its feel from the ones you pick.
8. **The four shapes:**
   - **A. Flat lines.** Each step is its own gray line with a chevron, under the question. The card sits in the transcript under the steps, as a bordered box.
   - **B. One summary line.** All steps of an exchange fold into one gray line ("3 steps") that opens to the list, and each step opens further. The card replaces the input row at the bottom until a choice is made.
   - **C. Timeline.** Steps are dots on a thin vertical line at the left of the exchange. The detail opens under its dot. The card is a larger node on the same line.
   - **D. Chips.** Steps are small gray capsules that wrap in one row. A click opens the detail in a box under the row. The card is a banner across the top of the panel, over the transcript.

## Global Constraints

- Never widen the sandbox past read-only plus approvals: `"sandbox": "read-only"` stays on `thread/start` and `thread/resume`; Pauri sends only `accept` and `decline`. (issue #5)
- The step lines are not sent back to the model. (issue #5)
- Button copy, exact: `Allow`, `Deny`, `Allow for this chat`.
- Nothing runs before a choice: Pauri replies to an approval request only from a click, or from the chat's "allow for this chat" flag.
- A server request Pauri does not handle still gets the method-not-found error at once, so a turn never waits on Pauri.
- Native Swift. No third-party package.
- Public repo: test fixtures use made-up paths (`/Users/u/...`), not the owner's.
- Commit format: `type(scope): summary (refs #5)`. Trailers: the harness default `Co-Authored-By` line, nothing else.

- [ ] **Step 4: Implement the chat side in `Chat.swift`**
