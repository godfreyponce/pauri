# #41 The up-arrow click installs the update at any zoom: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A click on the header's up-arrow installs the newer version at every zoom from 80% to 200%, and Pauri comes back with the panel open.

**Architecture:** Task 1 reproduces the bug on a dev build with a local update feed and finds out whether the failure follows the zoom; it changes no code, and it ends with a stop for the owner's clicks. Task 2 runs only if the failure follows the zoom: it removes #38's `ZoomView` (AppKit scales the bounds of a view above the `NSHostingView`) and does the zoom inside SwiftUI instead (`ZoomedContent`: lay out in `size / zoom`, then `.scaleEffect(zoom, anchor: .topLeading)`). AppKit then sees an unscaled hosting view at every zoom, which is the case the owner proved works (zoom 100). Task 2 proves the fix with the same local feed at 80%, 100%, 110%, and 150%.

**Tech Stack:** Swift, SwiftUI in an `NSHostingView`, AppKit `NSPanel`, Sparkle 2, Swift Testing.

**Spec:** Issue #41 and its comment of 2026-11-18 (the zoom-100 click installed 0.1.5; the zoom-110 click did not). No design spec in `docs/superpowers/specs/`. #38's plan, `docs/superpowers/plans/2026-11-17-issue-38.md`, records why `ZoomView` exists (spikes 1 to 3) and that synthesized clicks do not reach SwiftUI (spike 5).

## Data flow

No data-flow change: the fix changes only how the panel's content is scaled. `panelZoom`, `panelSize`, and the update feed are read and written as before.

## What is known (planning session, read-only)

- The up-arrow is `PanelView.swift:59-74`: a `Button` that calls `updater.install()`, disabled while `updater.isInstalling || !chat.canStartNewChat`. `install()` sends Sparkle's `.install` reply and sets `isInstalling` (the spinner shows).
- When no update is ready, `UpdateStatusIcon` (`PanelView.swift:274`) fills the same slot; its check-mark click calls `checkNow()` and shows a spinner for at least 1 second. So the same spot can be tested at 110% without an update.
- At zoom 100, `ZoomView`'s bounds equal its frame, so AppKit applies no scale. At any other zoom it does. That is the one thing that differs between the owner's working and failing clicks.
- #38's hand check step 4 asked for header clicks at 150%. Whether that was done and passed is not recorded.
- Synthesized clicks do not reach SwiftUI (#38 spike 5). The clicks in this plan are the owner's.
- The dev build is version 0.1.0 (`Support/Info.plist`, both version keys). It checks for updates only when `PauriTestFeedURL` is set.

## Gate 1 decisions (owner: change any of these before go)

1. **Prove first, then fix.** Task 1 reproduces the failure at 110% on a dev build and checks whether it follows the zoom live (Cmd+0 makes the same click work). The fix in Task 2 is prepared for that result only.
2. **The fix moves the zoom from AppKit into SwiftUI** (`ZoomedContent` with `.scaleEffect`). SwiftUI then owns both the drawing and the click mapping, and AppKit sees what it saw at zoom 100. Text softness away from 100% should be about the same as today; the owner judges it in the hand check. Alternative: keep `ZoomView` and look for the exact AppKit call that breaks. That is open-ended, with no test that can see a click.
3. **Stop rule.** If Task 1 gives a result that does not match the table in Task 1 Step 5 (the failure does not reproduce, it does not follow the zoom, or the spinner shows but no download starts), the builder stops, reports the results, and the ticket goes back to `/plan-ticket`. Task 2 is not built on a guess.
4. **The proof is a local feed on dev builds** (0.1.0 updates to a local 0.9.0), as in #28, #32, and #34. This build does not cut a release. After accept, the owner runs the release. Copies on 0.1.4 or 0.1.5 still have the broken click; their way to update is Cmd+0 first, then the up-arrow (the owner's own result), or `brew upgrade --cask pauri`. That line belongs in the release notes.
5. **The cause is named in the gate 2 report and in the close comment** (`gh issue close 41 --comment "<cause and fix in one line>"`), not in a comment posted before the owner accepts.
6. **`zoomViewGivesContentScaledRoom` is replaced, not kept.** It tests the `ZoomView` class this plan deletes. The new test checks that `ZoomedContent` gives its content `size / zoom` room. If a hosting view does not report that size in a test, the test is dropped and the gate 2 report says so; the hand check covers it.

### Task 2: Do the zoom in SwiftUI, so AppKit never scales the hosting view

**Files:**
- Modify: `Sources/Pauri/PanelController.swift` (the host setup at lines 29-34, `applyZoom` at 48-55, and `ZoomView` at 98-124 is deleted)
- Test: `Tests/PauriTests/PanelZoomTests.swift` (replace `zoomViewGivesContentScaledRoom` at lines 86-98)

**Interfaces:**
- Consumes: `PanelZoom.scale(_ percent: Int) -> CGFloat`, `PanelZoom.saved(in:)`, `PanelZoom.applied(_:to:frame:)` (unchanged).
- Produces, in `PanelController.swift`:
  - `@MainActor @Observable final class ZoomScale { var value: CGFloat; init(_ value: CGFloat) }`
  - `struct ZoomedContent<Content: View>: View`, with `let zoom: ZoomScale` and `@ViewBuilder let content: Content`. Body: a `GeometryReader` (it keeps the safe area, so the header stays under the title bar) whose content is `content.frame(width: size.width / zoom.value, height: size.height / zoom.value).scaleEffect(zoom.value, anchor: .topLeading)`.

- [ ] **Step 1: Replace the test.** Delete `zoomViewGivesContentScaledRoom`. Add `zoomedContentGivesContentScaledRoom` (`@MainActor`): an `NSHostingView` of 520 x 680 whose root is `ZoomedContent(zoom: scale) { Color.clear.onGeometryChange(for: CGSize.self, of: \.size) { box.size = $0 } }`, where `box` is a small reference type the test declares. After `layoutSubtreeIfNeeded()`:
  - `scale.value = 1.25` gives `box.size == CGSize(width: 416, height: 544)`;
  - `scale.value = 1.5` and the host's frame size `600 x 750` give `CGSize(width: 400, height: 500)`;
  - `scale.value = 1` gives `CGSize(width: 600, height: 750)`.
  These are the old test's values. If the host reports no size without a window, put it in an `NSWindow` as `zoomKeysLeavePanelFrameAlone` does with its panel. If it still does not report, drop the test (decision 6).
