# Model Picker, Fast Default, Web Search Toggle Implementation Plan (refs #4)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The input bar gets a model picker and a globe toggle. New chats ask `gpt-6.1-sol` at low reasoning effort on Codex's Fast tier. Another model applies from the next message. The globe is on by default: on, Codex searches the web live; off, it does not search.

**Architecture:** `CodexClient.launch()` also calls `model/list` and keeps the models. `Chat` holds the chat's `ModelChoice` and `searchesWeb`, and passes both to `CodexClient.ask`. Every `turn/start` carries `model`, `effort`, and `serviceTierForTurn`. Web search is the `web_search` config key, set through `config` on `thread/start` and `thread/resume`. When the globe changes mid-chat, the next `ask` reloads the thread (`thread/unsubscribe`, then `thread/resume` with the new config) before the turn. A `webSearch` item becomes one gray step line, "Searched the web for ...".

**Tech Stack:** Swift 6, SwiftPM, SwiftUI, Swift Testing. No new dependency.

**Spec:** `docs/spec.md` decisions 6, 7, 8, 14; issue #4. Blocker #2 is closed.

## Data flow

```text
codex app-server (codex-cli 0.169.0)
   |  model/list (new), at launch
   v
CodexClient.models (new) --> Chat.modelChoices (new) --> model Menu (new, PanelView.swift)
                                                              | pick
globe Button (new, PanelView.swift) --> Chat.searchesWeb (new) |
                                              |                 v
                                              +--------> Chat.model (new)
                                              |                 |
                                              v                 v
                         CodexClient.ask(prompt, model:, searchesWeb:) (changed)
                                              |
   +------------------------------------------+-------------------------------------+
   | thread/start, thread/resume              | globe changed since the thread      | turn/start (changed)
   |   + config.web_search (changed)          | loaded: thread/unsubscribe (new)    |   + model, effort,
   |   "live" when on, "disabled" when off    |   then thread/resume + config (new) |     serviceTierForTurn
   v                                          v                                     v
codex app-server ----------- item/started, item/completed type "webSearch" -------> ToolStep (changed)
                                                                                    "Searched the web for ..."
                                                                                     --> ToolStepRow
```

Nothing is saved to disk by Pauri for this ticket: the model and the globe live in `Chat`, in memory.

## Gate 1 decisions (owner: change any of these before go)

1. **"Sol 6.1 fast" = `gpt-6.1-sol`, effort `low`, service tier `priority` (Codex's Fast: 2x speed, more usage).** It is the first picker entry, named "GPT-6.1-Sol Fast", and every new chat starts on it. The id is a constant in code, so the PR can name it. Alternative: standard tier (`serviceTierForTurn: "default"`), which does not use up the plan faster.
2. **The picker is the Fast entry plus every model from `model/list`, each at its own `defaultReasoningEffort` and standard speed.** Labels are `displayName`; the menu item's help is `description`. If `model/list` fails, the picker holds only the Fast entry. No effort or tier sub-menus. Alternative: a fixed list in code (goes stale with every codex update).
3. **The picker and the globe reset with each new chat and at launch** (Fast entry, globe on). Neither is saved. One rule for both controls, and it keeps "new chats default to a fast model" true. Alternative: remember the last pick (UserDefaults).
4. **Globe on = `web_search: "live"`, off = `"disabled"`.** `"cached"` reads an index that may not have today's news, and the ticket asks for current facts. Alternative: `"cached"` (cheaper, may be stale).
5. **A globe change mid-chat applies from the next message**, by reloading the thread with the new config (Task 1 must prove this works). If the chat has had no turn yet, Codex has not saved it, so Pauri starts a new thread with the new config instead. If Task 1 shows the reload does not change search, the build stops and asks; the fallback is "the globe applies from the next new chat", said in its tooltip.
6. **A web search shows as one gray step line**, "Searched the web for “query”", with the query as its detail (decision 13). This also lets the live tests see whether Codex searched.
7. **No 4-variant visual pass.** The picker is a stock borderless `Menu` with a `cpu` symbol and the short model name; the globe is a borderless `Button` with SF Symbol `globe`, accent color when on, secondary when off. Both sit between the text field and the mic. Same call as #1, #3, #6, #9, #11, #12: the look belongs to the spec's Fog item "a design-directions pass once the bones work". Say no here and Task 2 starts with `design-directions/issue-4.html`, references first.

## Global Constraints

- No direct OpenAI API calls (ticket constraint). Everything goes through `codex app-server`.
- Never write the user's Codex config (`config/value/write`, `config/batchWrite`): the overrides go in per-thread `config` only.
- `model/list` is read once per launch, one page, no `includeHidden`.
- Public repo: no env values, credentials, or owner personal data in code, tests, or commits. The model ids are public product names, not personal data.
- Live tests that run a turn carry `.timeLimit(.minutes(3))`, so a stalled turn fails the test instead of hanging the suite.

## Review Focus

1. **The reload between turns** (`ask` when the globe changed): it must not run while a turn streams, must keep `threadID`, and must not show old turns again (`restoredExchanges` is not touched by it).
2. **Effort is always sent.** Without it the owner's config makes every turn "medium".
3. **`serviceTierForTurn`, not `serviceTier`.** The per-turn field never changes the thread's stored tier, so a later pick of a standard entry really runs at standard speed.
4. **Approval during a live web-search test.** The tests decline any approval, so a test can never hang on a card nobody answers.

```swift
struct ModelChoice: Equatable, Sendable, Identifiable {
    let model: String          // e.g. "gpt-6.1-sol"
    let name: String           // menu label
    let effort: String         // e.g. "low"
    let serviceTier: String    // "priority" or "default"; sent as serviceTierForTurn
    let help: String
    var id: String { model + "/" + serviceTier }

    static let quick = ModelChoice(model: "gpt-6.1-sol", name: "GPT-6.1-Sol Fast", effort: "low",
                                   serviceTier: "priority", help: "Fast answers at low reasoning effort.")
    /// `[.quick]` followed by each model at its default effort and standard speed.
    static func menu(_ models: ModelListResult) -> [ModelChoice]
}

struct ModelListResult: Decodable { /* data: [{ id, displayName, description, defaultReasoningEffort }] */ }

// CodexClient
private(set) var models: ModelListResult?   // nil when model/list failed
func ask(_ question: String, model: ModelChoice, searchesWeb: Bool) -> AsyncThrowingStream<TurnEvent, Error>
nonisolated static func webSearchConfig(_ on: Bool) -> [String: Any]   // ["web_search": "live" | "disabled"]
```
