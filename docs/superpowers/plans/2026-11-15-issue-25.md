# Handoff and Chat Open No Longer Race the Open Chat's Delete Implementation Plan (refs #25)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** While the open chat is being deleted, a handoff refuses (so it never asks the deleted thread and never blocks the delete's `newChat()`), and a chat opened from a reopened palette stays open after the delete ends.

**Architecture:** Two guards in `Chat`, no new state. `writeHandoff()` refuses while `isDeletingOpenChat` (#24's flag), the same way `send` does. `delete(_:)` starts a new chat at the end only if the deleted thread is still the client's open thread; an open that began during the delete has already moved `client.threadID` to its own thread (`CodexClient.resume` sets it before it awaits Codex), so that chat is left alone.

**Tech Stack:** Swift 6, SwiftPM, SwiftUI (macOS 14), Swift Testing. No new dependency.

**Spec:** issue #25 (no design spec). Background: `docs/superpowers/plans/2026-11-15-issue-24.md` and #24's section in `docs/HISTORY.md`.

## Data flow

No data-flow change: only the guard logic inside `Chat.writeHandoff()` and `Chat.delete(_:)` changes; `thread/delete`, `thread/fork`, `thread/resume`, and the remembered ID list are read and written as before.

## Global Constraints

- No change to the two-press delete or to the palette's look (#22). (issue #25, Constraints)
- Keep #24's behavior: send waits while the open chat is deleted, and the typed text stays. (issue #25, Constraints) `send`'s guard, the orb's `isEnabled`, and `isDeletingOpenChat`'s set/clear lines in `delete(_:)` stay as they are.
- **Gate 1 decision: open is not blocked during the delete.** Blocking `Chat.open` would make the palette close (`HistoryList.open()` calls `close()` right after `chat.open`) with no chat opened, which breaks Done when 2; dimming the rows instead is a palette look change the ticket forbids.
- **Gate 1 decision: the context banner keeps its look during the delete.** Its "Write a handoff draft" button stays on and a click during the delete does nothing (`writeHandoff()` returns nil). The delete lasts well under a second and the banner disappears when it ends (the new chat has no context usage). The alternative is `isEnabled: chat.canStartNewChat && !chat.isDeletingOpenChat` in `PanelView.swift:117`, which also dims the banner's New chat button.
- **Gate 1 decision: a failed open that ends after the delete is not covered.** If the delete returns while chat B's resume is still waiting, and that resume then fails, `CodexClient.resume` puts the deleted thread back as the open one and the next send fails. It needs a resume failure inside a sub-second window, and no live call can force that order. Left out; filed as an issue at accept if the owner wants it.
- `canStartNewChat` and its doc comment do not change (#24's gate 1 decision).
- No visual-rule variants: nothing visual changes.
- Public repo: no env values, credentials, or owner personal data in code, tests, or commits.

## Review Focus

1. **Handoff clicked during the open chat's delete.** Expected: nothing is written, no notice, and after the delete an empty "New chat" whose first question goes to a new thread and gets an answer. Pinned by `liveHandoffWaitsWhileTheOpenChatIsDeleted` (Step 1).
2. **Chat B opened during the open chat's delete, B's resume replying first.** Expected: B's turns stay, `client.threadID` is B, and the next question goes to B. Pinned by `liveChatOpenedDuringTheOpenChatsDeleteStays` (Step 1). The order of Codex's two replies is not under the test's control; see Step 2.
3. **Same, the delete replying first.** Expected: the same end state. The same test covers it when Codex replies in that order; before this ticket that order already worked (`newChat()` was skipped while `isOpening`).
4. **Opening the chat that is being deleted, from a reopened palette.** Real behavior, not changed by this ticket's code: if that chat's resume has finished (or failed) when the delete ends, the deleted thread is still `client.threadID` and the delete starts a new chat. If the resume is still waiting when the delete ends, `newChat()` is skipped by `canStartNewChat` (`isOpening`), as before this ticket, and the panel is left on the deleted thread, so the next send fails. No automated test (the same reply-order problem) and no code change for it (coordinator note at gate 1); the gate 2 closing states this behavior, and the HISTORY section's "Not covered" line carries it.
5. **Deleting a chat that is not open, and #24's send guard.** Expected: unchanged. Covered by the existing `liveDeleteDropsTheChatAndTheOpenOneStartsNew`, `liveSendWaitsWhileTheOpenChatIsDeleted`, and `liveDeletingAnotherChatKeepsSendWaiting`, which must still pass.

- [ ] **Step 1: Write the two live tests** in `CodexClientLiveTests.swift`, after `liveDeletingAnotherChatKeepsSendWaiting`, each with the trait `@Test(.enabled(if: ProcessInfo.processInfo.environment["PAURI_LIVE"] == "1"))`. They use the file's private `freshDefaults`, `waitUntil`, and `quit`, and the same one-`Task.yield()` start as #24's tests.

```swift
@MainActor func liveHandoffWaitsWhileTheOpenChatIsDeleted() async throws {
    let client = CodexClient(defaults: freshDefaults("pauri-live-delete-handoff"))
    let chat = Chat(client: client)
    chat.warmUp()
    try await waitUntil { !chat.isStarting }
    #expect(chat.send("what is 2+2"))
    try await waitUntil { !chat.isAnswering }
    let open = try #require(client.threadID)

    let deleting = Task { try await chat.delete(open) }
    await Task.yield()
    #expect(chat.isDeletingOpenChat)
    let note = await chat.writeHandoff()
    #expect(note == nil)
    #expect(!chat.isWritingHandoff)
    try await deleting.value

    #expect(chat.notice == nil)
    #expect(chat.exchanges.isEmpty)
    #expect(client.threadID == nil)
    #expect(chat.send("what is 5+5"))
    try await waitUntil { !chat.isAnswering }
    let next = try #require(client.threadID)
    #expect(next != open)
    #expect(chat.exchanges.count == 1)
    #expect(chat.exchanges[0].answer.contains("10"))
    try await quit(client)
}

/// Codex may reply to the delete or to the resume first; the chat opened must stay either way.
@MainActor func liveChatOpenedDuringTheOpenChatsDeleteStays() async throws {
    let client = CodexClient(defaults: freshDefaults("pauri-live-delete-open"))
    let chat = Chat(client: client)
    chat.warmUp()
    try await waitUntil { !chat.isStarting }
    #expect(chat.send("what is 2+2"))
    try await waitUntil { !chat.isAnswering }
    let other = try #require(client.threadID)
    chat.newChat()
    #expect(chat.send("what is 3+3"))
    try await waitUntil { !chat.isAnswering }
    let open = try #require(client.threadID)

    let deleting = Task { try await chat.delete(open) }
    await Task.yield()
    #expect(chat.isDeletingOpenChat)
    chat.open(other)
    #expect(chat.isOpening)
    try await waitUntil { !chat.isOpening }
    try await deleting.value

    #expect(chat.notice == nil)
    #expect(client.threadID == other)
    #expect(chat.exchanges.map(\.question) == ["what is 2+2"])
    #expect(chat.send("what is 5+5"))
    try await waitUntil { !chat.isAnswering }
    #expect(client.threadID == other)
    #expect(chat.exchanges.count == 2)
    #expect(chat.exchanges[1].answer.contains("10"))
    try await quit(client)
}
```

`chat.open(other)` is called directly, not through the palette: its `canStartNewChat` guard passes during the delete, as the palette's does once reopened.
