# Default Model From Codex's Model List Implementation Plan (refs #15)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** New chats start on the model Codex marks `isDefault`, not on a model id written into Pauri, and a question still gets an answer when `model/list` fails.

**Architecture:** `ModelChoice.quick` goes away. `ModelChoice.menu` builds the first entry from the visible model with `isDefault: true`: low effort only if the model lists it, the `priority` tier and the word "Fast" only if the model lists that tier. `ModelChoice.serviceTier` becomes optional; nil sends no `serviceTierForTurn`. `Chat.model` becomes optional; nil sends no `model`, so Codex uses its own default. That is the state before the list arrives and after `model/list` fails.

**Tech Stack:** Swift 6, SwiftPM, SwiftUI, Swift Testing. No new dependency.

**Spec:** issue #15; `docs/spec.md` decision 7 (rewritten by this plan).

## Data flow

No data-flow change: `model/list` is still read once at launch and `turn/start` is still the only writer; the ticket changes only which fields `turn/start` carries (no `model` when the list failed, no `serviceTierForTurn` when the default model has no Fast tier).

- `v2/TurnStartParams.ts`: `serviceTierForTurn` omitted or null "inherits the thread's tier"; `"default"` means standard speed.

## Decisions for gate 1

1. **"Fast" follows the tier, effort is separate.** The ticket's two checks are applied one at a time: `effort` is `"low"` if the default model lists `low`, else its `defaultReasoningEffort`; `serviceTier` is `"priority"` and the name gets `" Fast"` if it lists `priority`, else `serviceTier` is nil and the name is the plain `displayName`. Help text is `"Fast answers at low reasoning effort."` only when both hold, else the model's `description`. The other reading (Fast is all or nothing: low and priority together, or neither) would be a one-line change.
2. **No duplicate line.** When the default entry has no Fast tier, it takes the place of that model's standard-speed line in the picker, so the picker never shows the same name twice. When it is Fast, the menu is as today: the Fast entry, then every model at standard speed.
3. **No `isDefault` model (or it is hidden):** no special entry; the picker lists the visible models and a new chat takes the first one. An empty list: no entries, `Chat.model` stays nil, no `model` is sent.
4. **Picker label when no model is picked:** `"Codex default"`, and the menu is disabled while `modelChoices` is empty (before the list arrives and after `model/list` fails). This is one label string and one `.disabled` on the existing control, so the 4-variant visual rule is not applied. Say so at gate 1 if you want variants.
5. **Live tests send no model.** The shared live helpers (`answer`, `run`) and the direct `client.ask(..., model: .quick, ...)` calls switch to `model: nil`, so no live test hard-codes a model id. They then run on the owner's own Codex config (`model_reasoning_effort = "medium"`), which is slower than low effort. `liveModelListAndFastDefaultAnswer` is the one live test that runs the real default entry.
6. **Known gap:** a question sent in the first moment after launch, before `model/list` returns, goes with `Chat.model == nil`, so that one turn runs on Codex's own default. Before this ticket it ran on the hard-coded Fast entry. It is not fixed here; say so if it should be.
