# Whole-Panel Redesign: Four Variants, Owner Picks, Wire the Winner Implementation Plan (refs #21)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One design page shows four different shapes for the whole panel (header, message list, empty state, spacing and type), each also showing where the Cmd+K history list will live. The owner picks one, and the picked panel is wired into SwiftUI with the orb, input area, and model picker unchanged.

**Architecture:** Task 1 builds `design-directions/issue-21.html` and the build stops for the owner's pick. Task 2 rebuilds the panel's chrome in `PanelView.swift` to the winner (header, transcript layout, a new empty state, spacing and type), touches the four helper views for spacing and type only, updates the README if a control moved, and runs the hand checks and the full check. No model, protocol, or client code changes.

**Tech Stack:** Swift 6, SwiftPM, SwiftUI (macOS 14). One static HTML page. No new dependency.

**Spec:** issue #21; parent #19 (decisions 1 to 4); `docs/spec.md` decision 11; siblings #20 (plain Cmd+K list) and #22 (history surface in the picked design, blocked by this ticket). Earlier picks that stay fixed: `design-directions/issue-10.html` (send orb), `design-directions/issue-17.html` variant A (input area and model picker).

## Gate 1 decisions (owner: change any of these before go)

1. **The pick happens at a stop after Task 1, not at gate 1.** The ticket says "the owner picks one at gate 1". In this repo the page has always been built by the build session, which then stops for the pick (#5, #8, #16, #17), and this plan does the same: after go, Task 1 builds the page and stops; Task 2 waits for your pick. No Swift changes before the pick. Alternative: the planner builds the page now, before go, so the pick is literally at gate 1.
2. **References:** `docs/reference/chatgpt-window.png` and Raycast AI chat, for feel and not layout (fixed by the ticket). The page cannot load a remote image. If you want Raycast shown on the page, send a screenshot in your reply and Task 1 saves it as `docs/reference/raycast-ai-chat.png`; otherwise the page names Raycast in its lede only.
3. **The four shapes** (each one differs in its chrome and in where history lives):
   - **A. No header bar.** The transcript runs to the top edge. History, new chat, and settings sit in a small floating icon pill at the top right. History opens as a popover under the pill: a search field on top, then the chats grouped by day (Today, Yesterday, Earlier), a trash icon on hover. Full-width answers, as in the ChatGPT window. Empty state: one short centered line and three hint rows.
   - **B. Toolbar and sidebar.** A real toolbar row: a sidebar toggle on the left, the chat title in the middle, new chat and settings on the right. Cmd+K slides a sidebar in from the left inside the panel, over the transcript: search on top, chats by day, delete on hover. Empty state: a left-aligned greeting with the hotkey and Cmd+K shown as key caps.
   - **C. Command palette.** Raycast-like and dense: a slim header with the chat title on the left and small icons on the right. Cmd+K covers the whole panel with a search field and a full-height list (title, first line of the chat, date, delete), keyboard-first; Esc returns. The message list uses compact rows: the user's message as a labeled row, not a bubble, and answers under it. Empty state: a short list of suggested actions.
   - **D. Home screen.** No title in the header, only a back-to-home icon on the left and settings on the right. The empty state is the home: a greeting, then a search field and the recent chats under it. Cmd+K opens the home and focuses its search. During a chat the header holds only the home icon and settings.
4. **This ticket wires only the panel parts that need no new data.** No chat title in the header (the titles arrive with #20) and no history button, popover, sidebar, palette, or home list (#22 builds the history surface). If the winner has a slot for any of these, Task 2 leaves the slot out and adds one comment on #22 that names what was left out. For D, the wired home shows the greeting only, and its search and list come with #22.
5. **The empty state shows when `chat.exchanges.isEmpty && !chat.isStarting`.** At launch the old turns arrive only after Codex starts, so this rule keeps the empty state from showing for a moment and then giving way to the restored chat. During the start the transcript stays blank, as today.
6. **The message list is in scope; the rendering is not.** Variants may change the user message's shape, width, and alignment, the gaps, the answer's font size and line spacing, and the panel's padding. `MarkdownView`'s block logic, `ToolStepRow`'s expand behavior, `ApprovalCard`'s buttons, and `ContextBanner`'s copy and yellow stay as they are; those four files change only in font sizes, paddings, gaps, and corner radii.
7. **The panel stays 520 x 680 on the same `.popover` glass.** `PanelController.swift` changes only if the winner needs a different default height. B's sidebar is drawn inside the 520 pt panel.
8. **#20 may run at the same time.** It adds a Cmd+K hook to `PanelView.swift` and a new `HistoryList.swift`. Whichever ticket lands second merges main into its branch before its last task.
