# Ask One Question, Get a Streamed Answer Implementation Plan (refs #2)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Return in the panel sends the question to one warm `codex app-server` child process and streams the answer into the panel. When `codex` is missing or logged out, the panel says what to do.

**Architecture:** `CodexProtocol.swift` is pure: it parses one JSON line from the server into a Sendable enum, builds the reply to server requests, and parses the shell lookup output. `CodexClient` (main actor) finds `codex` through the user's login shell, spawns `codex app-server` once, speaks newline-delimited JSON-RPC over its stdin and stdout, and turns a question into an `AsyncThrowingStream` of text deltas. `Chat` (an `@Observable` model) holds the answer and the notice that `PanelView` shows.

**Tech Stack:** Swift 6, SwiftUI, AppKit, Foundation `Process`, Swift Testing. No new dependency.

**Spec:** `docs/spec.md` decisions 5, 6, 9; issue #2.

## Data flow

```text
PanelView TextField, Return (changed)
   |
   v
Chat (new) --ask--> CodexClient (new)
   ^                   |
   |                   +-- on launch, and again after a failed start:
   |                   |     $SHELL -l -i -c '<lookup>'  --> codex path + the shell's PATH
   |                   |
   |                   +-- stdin, one JSON line per message --> codex app-server (new child process)
   |                   <-- stdout, one JSON line per message --+     |
   |                   |                                             +--> ~/.codex (config, login; Pauri never opens it)
   +-- text deltas ----+                                             +--> ~/.codex/sessions (Codex saves the thread)
   |                                                                 +--> OpenAI, through the user's ChatGPT login
   v
PanelView answer text (changed)
Chat --> NSLog "Pauri: first token after N ms" --> unified log (new)
```

## What the probe found (2026-11-13, codex-cli 0.167.2, this Mac)

`codex app-server generate-ts` gives the protocol types. A Python probe in the planning
session's scratchpad drove the real server. Facts the build relies on:

- Transport: one JSON object per line on stdin and stdout. No `"jsonrpc"` field is needed. Requests
  carry `id`; responses carry the same `id` with `result` or `error`; notifications carry `method`
  and `params` and no `id`. A message with both `id` and `method` is a request from the server.
- Handshake: `initialize` request, then an `initialized` notification. The `initialize` response
  arrived in 0.28 s.
- Login: `account/read` with `{}` returns `"account": null` when logged out (probed with an empty
  `CODEX_HOME`), and an object with `"type": "chatgpt"` when logged in. `requiresOpenaiAuth` is
  `true` in both cases, so do not use it. The logged-in reply carries the email: never log or store it.
- `thread/start` returns `result.thread.id`, the model, and the effort. The default here is
  `gpt-6.1-sol` at `medium`.
- `turn/start` returns at once. Then `item/agentMessage/delta` notifications carry
  `params.delta`, and `turn/completed` carries `params.turn.status` (`completed`, `interrupted`,
  `failed`, `inProgress`) and `params.turn.error.message` when it failed. An `error` notification
  carries `params.error.message` and `params.willRetry`.
- `codex` on this Mac is `~/.nvm/versions/node/v24.14.1/bin/codex`, a `#!/usr/bin/env node`
  script. So the child process needs a `PATH` that has `node` on it, not only the codex path. On
  Node 24 the script `execve`s the native binary, so it is one process.
- `$SHELL -l -c 'command -v codex'` finds nothing (nvm loads in `.zshrc`). `$SHELL -l -i -c`
  finds it, in 0.50 s from a clean environment.
- Closing stdin makes the server exit with code 0.
- Time from `turn/start` to first delta, short question ("Reply with just the word hi."):

  | Case | ms |
  |---|---|
  | First turn on a new thread, fresh process | 3191, 3130, 2869 |
  | Second new thread, same process | 2729 |
  | Second turn, same thread, default effort | 1846 |
  | Second turn, same thread, `effort: "low"` | 1676 |

  Each turn sends about 16.7k input tokens (Codex's base prompt plus the user's MCP tools
  `codex_apps`, `cua_repl`, `node_repl`). Low effort barely helps. About one second needs a faster
  model, which is #4.

## Gate 1 decisions (owner: change any of these before go)

1. **One Codex thread per launch, reused for every question.** It is started during warm-up, before the first Return. Measured: a second turn on the same thread got its first token in 1.8 s, a new thread in 2.7 s. The cost: Codex remembers the earlier questions of this launch, but the panel shows only the latest answer. #3 makes the thread visible and adds Cmd+N. The other choice is a new thread per question: about 0.9 s slower each time, and no hidden memory.
2. **Codex's own default model and effort, no override.** On this Mac that is `gpt-6.1-sol` at medium. The measured first token will be about 1.7 to 3.2 s, not about 1 s. The gate 2 report gives the real number and says that the fast default is #4. Passing `effort: "low"` now saved only about 0.2 s in the probe, so this plan does not do it.
3. **Read-only sandbox, approval policy `never`.** With `never`, Codex does not ask, and a step that needs a write fails inside Codex. Pauri replies to any request from the server with a JSON-RPC error (`-32601`), so a turn cannot hang while it waits for Pauri. #5 changes the policy to asking and adds the approval cards.
4. **Find `codex` through the user's interactive login shell, once per start.** The shell runs `$SHELL -l -i -c` with stdin from `/dev/null`, and Pauri takes both the codex path and the shell's `PATH`. This finds nvm, Homebrew, Volta, or any install that works in the user's Terminal. Measured cost: 0.5 s, during warm-up at launch. The other choice is a fixed list of folders, which misses custom installs and still has to find `node`. No timeout: none has a measured basis, and stdin from `/dev/null` stops an rc file that waits for input.
5. **Not a visual ticket.** The answer is plain, selectable text above the input field. It shows no Markdown rendering and does not scroll itself to the end. The look is #9, #10, and the spec's Fog design pass, where the visual rule applies.
6. **Thread working folder is the home folder.** A GUI app starts in `/`. Read-only tools then see the user's files the same way a Terminal `codex` does.
7. **The first-token time is an `NSLog` line that stays in the app:** `Pauri: first token after N ms`. The ticket asks for the number. #4 needs the same number to check the fast default.
8. **Copy for the two setup problems.** Not installed: "Pauri can't find Codex. Install it with `npm install -g @openai/codex`, then ask again." Not logged in: "Codex isn't logged in. Run `codex login` in Terminal, then ask again." Each new Return retries the start, so Pauri does not need a restart.

## Global Constraints

- No direct OpenAI API calls. Pauri talks only to the `codex app-server` child.
- Pauri never reads or stores OpenAI credentials. It does not open anything under `~/.codex`, does not read `OPENAI_API_KEY`, and keeps nothing from `account/read` except whether `account` is null.
- `thread/start` uses `"sandbox": "read-only"` (spec decision 9).
- One question, one answer. No follow-up UI (#3), no model picker (#4), no tool lines or approval cards (#5).
- No new dependency.
- Public repo: no env values, credentials, emails, or owner personal data in commits or test fixtures.
- Commit form, from AGENTS.md `# Commit format`: `type(scope): summary (refs #2)`. Trailers: the harness default `Co-Authored-By` line, nothing else.
- STATE.md is not touched in this build.

## Review Focus

1. **Return before warm-up finishes** (in the first second after launch): the question waits for the start that is already running. It must not spawn a second process. `start()` joins an in-flight start. The live test in Task 2 calls `start()` twice at once and checks that one pid serves both questions.
2. **Codex dies mid-answer** (crash, or `pkill -f "codex app-server"`): the answer stops, the panel says "Codex stopped. Ask again to restart it.", and the next Return spawns a new process. Manual check 5.
3. **Logged out, then `codex login`, then Return without restarting Pauri:** the answer streams. A failed start terminates its process, and the next start spawns a fresh one that reads the new login. Manual check 4.
4. **`codex` not findable:** the panel shows the install message at launch and on every Return. It does not hang or crash. `parseCodexLookup` tests in Task 1 and manual check 3.
5. **Pauri quits (`pkill -x Pauri`):** no orphan `codex app-server` is left. The child's stdin closes and the server exits. Manual check 6.

### Task 1: Protocol messages and the codex lookup parser

**Files:**
- Create: `Sources/Pauri/CodexProtocol.swift`
- Test: `Tests/PauriTests/CodexProtocolTests.swift`

**Interfaces:**
- Produces, all in `CodexProtocol.swift`:
  - `enum RPCID: Equatable, Sendable { case int(Int), string(String) }`
  - `enum CodexNotification: Equatable, Sendable { case agentMessageDelta(String); case turnCompleted(errorMessage: String?); case error(message: String, willRetry: Bool); case ignored }`
  - `enum CodexIncoming: Equatable, Sendable { case response(id: Int, result: Data); case failure(id: Int, message: String); case request(id: RPCID); case notification(CodexNotification) }` with `init(line: Data) throws`. `result` is the `result` object written back to JSON, for the caller to decode.
  - `struct AccountReadResult: Decodable { var isLoggedIn: Bool }`: decodes `account` as an optional object that has only `type`. `isLoggedIn` is `account != nil`. Do not decode the email.
  - `struct ThreadStartResult: Decodable { let thread: ThreadRef }`, `struct ThreadRef: Decodable { let id: String }`
  - `enum CodexOutgoing { static func request(id: Int, method: String, params: [String: Any]) -> Data; static func notification(method: String) -> Data; static func unsupported(id: RPCID) -> Data }`. Each returns one JSON object plus `"\n"`, built with `JSONSerialization`. Use `NSNull()` for a JSON `null`.
  - `struct CodexLocation: Equatable, Sendable { let executable: String; let path: String }`
  - `let codexLookupMarker = "__PAURI__"` and `let codexLookupScript = #"printf '%s\n' __PAURI__ "$(command -v codex)" "$PATH""#`
  - `func parseCodexLookup(_ output: String) -> CodexLocation?`: finds the line equal to the marker and takes the two lines after it. Returns nil when the codex line is not an absolute path. That covers an empty line, and zsh's `alias codex=...` output.

`turn/completed` maps to `errorMessage: nil` when `turn.status` is `completed`. For any other status it maps to `turn.error.message`, or to `"Codex ended the answer (<status>)."` when there is no error. Every method not listed above maps to `.ignored`.

### Task 2: CodexClient, one warm app-server process

**Files:**
- Create: `Sources/Pauri/CodexClient.swift`
- Test: `Tests/PauriTests/CodexClientLiveTests.swift`

**Interfaces:**
- Consumes: everything in Task 1's Interfaces block.
- Produces:
  - `enum CodexProblem: Error, Equatable { case notInstalled, notLoggedIn, stopped, failed(String); var message: String }`. Use this exact copy for `message`:
    - `notInstalled`: `Pauri can't find Codex. Install it with npm install -g @openai/codex, then ask again.`
    - `notLoggedIn`: `Codex isn't logged in. Run codex login in Terminal, then ask again.`
    - `stopped`: `Codex stopped. Ask again to restart it.`
    - `failed(let text)`: `text`
  - `@MainActor final class CodexClient { init(); private(set) var processIdentifier: Int32?; func start() async throws; func ask(_ question: String) -> AsyncThrowingStream<String, Error> }`. Errors thrown are `CodexProblem`.

**Behavior, in the order it runs:**

1. `start()` returns at once when a start already succeeded and the process is alive. When a start is running, it awaits that same `Task` (Review Focus 1). Otherwise it creates the `Task` and stores it. If that task fails, it clears the stored task and terminates any process it spawned, so the next call starts over (Review Focus 3).
2. Lookup: run `ProcessInfo.processInfo.environment["SHELL"] ?? "/bin/zsh"` with arguments `["-l", "-i", "-c", codexLookupScript]`. Set stdin and stderr to `FileHandle.nullDevice` and stdout to a pipe. Wait for exit off the main thread, for example with `terminationHandler` and a checked continuation. Run `parseCodexLookup` on the output. A nil result, or a shell that fails to launch, throws `.notInstalled`.
3. Spawn: set `executableURL` to the codex path and `arguments` to `["app-server"]`. Use Pauri's environment with `PATH` replaced by the looked-up `path`. Set `currentDirectoryURL` to the home folder, stdin and stdout to pipes, and stderr to `FileHandle.nullDevice`. A pipe nobody reads fills up and blocks the child. Store `processIdentifier`.
4. Reader: a `Task` loops over `stdout.fileHandleForReading.bytes.lines` and parses each line with `CodexIncoming(line:)`. A line that does not parse is skipped. The reader handles each kind of message:
   - `.response` and `.failure` resume the pending continuation stored under that id. A failure resumes with `CodexProblem.failed(message)`.
   - `.request(id)` writes `CodexOutgoing.unsupported(id:)` at once (gate 1 decision 3).
   - `.agentMessageDelta(text)` yields `text` to the active stream.
   - `.turnCompleted(nil)` finishes the active stream. `.turnCompleted(message?)` finishes it, throwing `.failed(message)`.
   - `.error(message, willRetry: false)` finishes the active stream, throwing `.failed(message)`. `willRetry: true` is ignored.
5. Termination: the process `terminationHandler` hops to the main actor. There it fails every pending continuation and the active stream with `.stopped`, and clears the process, the pid, the thread id, and the stored start task (Review Focus 2).
6. Handshake. Request ids count up from 1 and stay unique for the life of the client. Send these lines:
   - `{"id":N,"method":"initialize","params":{"clientInfo":{"name":"pauri","title":"Pauri","version":V},"capabilities":null}}`, where `V` is `CFBundleShortVersionString`, or `"dev"` when it is missing (under `swift test`).
   - `{"method":"initialized"}`
   - `{"id":N,"method":"account/read","params":{}}`. When `isLoggedIn` is false, terminate the process and throw `.notLoggedIn`.
   - `{"id":N,"method":"thread/start","params":{"cwd":"<home folder path>","sandbox":"read-only","approvalPolicy":"never"}}`. Keep `thread.id`.
7. `ask(question)` returns a stream whose producer `Task` first awaits `start()`. A thrown start error finishes the stream. Then it stores the stream's continuation as the active one and sends `{"id":N,"method":"turn/start","params":{"threadId":T,"input":[{"type":"text","text":Q,"text_elements":[]}]}}`. A failure response finishes the stream. One question at a time: `Chat` guarantees it, so no queue is needed.
