# Live Screenshot Test Passes Every Time at the Default Effort Implementation Plan (refs #18)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `liveImageIsDescribedAndOutlivesItsFile` runs on Pauri's default model entry (low effort) and passes 4 of 4, and its follow-up proves it still sees the image after the file is gone.

**Architecture:** Test-only change. The cause is in the test, not in `CodexClient`: the 64x64 test image gets its halves swapped by the low-effort model, and the first check does not check order. The test moves to a 512x512 image, sends the default entry from `model/list` on both turns, and asks about the left half first and the right half in the follow-up.

**Tech Stack:** Swift 6, SwiftPM, Swift Testing. No new dependency.

**Spec:** issue #18. No design spec.

## Data flow

No data-flow change: only the live test's image size, prompts, checks, and the model it sends change; `CodexClient` and every file it reads or writes stay as they are.

## The cause, with evidence

Probes on 2026-11-14 (codex-cli 0.169.0, this Mac). A scratch Python script outside the repo replayed the test's two turns against `codex app-server` with the same `thread/start` params (`read-only`, `on-request`, `web_search = "live"`), the same `localImage` input, and the image file deleted between the turns. "default" means the params Pauri's picker starts on: the `isDefault` model from `model/list` with `effort: "low"` and `serviceTierForTurn: "priority"` (today `gpt-6.1-sol`), sent on both turns.

| Image | Prompts | Runs | First answer | Follow-up | Test check |
|---|---|---|---|---|---|
| 64x64 | today's | 5 | "Red, then blue." / "Blue, then red." / "Blue, red." / "Red, blue." / "Red, blue." | "Red" / "Blue" / "Blue" / "Red" / "Red" | 3 of 5 |
| 512x512 | today's | 4 | "Red, blue." (all four) | "Red" (all four) | 4 of 4 |
| 512x512 | left half, then right half | 4 | "Red" (all four) | "Blue" (all four) | 4 of 4 |

What this shows:

1. **The follow-up does not lose the image.** In every run the follow-up agrees with the first answer, and in the third row it names a color the first answer never said ("Blue"), with the file already deleted. Both turns carry the same `model`, `effort`, and `serviceTierForTurn`. So the product is not the cause.
2. **The miss is in the first turn.** At low effort the model read the 64x64 image as blue-left in 2 of 5 runs. The first check (`contains("red") && contains("blue")`) does not check order, so the swap passes turn 1 and shows up as "the follow-up named the wrong color".
3. **Image size is the trigger.** The same low-effort turn read a 512x512 image right 8 of 8 times. Pauri's real screenshots are a whole screen at point size, far larger than 64x64.
4. **Today the test does not run at the default effort.** #15 switched the live tests to `model: nil`, so this test now runs on the owner's own Codex config (`model_reasoning_effort = "medium"`), which already passed 4 of 4 in #4. It would pass today without proving anything about the default.
5. **Today's follow-up proves little.** "Name the left color again" can be answered from the first answer's text alone, with no image at all.

## Global Constraints

- Do not loosen the checks (issue #18 Constraints). Each check below is stricter than today's.
- Live runs spend tokens: the four proof runs, plus at most one rerun if a run fails for a reason outside the test (network, login). Do not rerun to collect a pass.
- Public repo: no account details or personal paths in the test.
- `Sources/` is not touched.

## Decisions for gate 1

1. **Fix the test, not the product.** No effort raise when a screenshot is attached. The miss came from a 64x64 synthetic image; a 512x512 one passed 8 of 8 at low effort. A user-facing raise would cost every screenshot question speed for a problem the probes did not show on screen-sized images. Say so if you want the raise anyway; it would be a separate ticket.
2. **The test sends Pauri's default entry, `ModelChoice.menu(models).first`, on both turns,** the way `liveModelListGivesADefaultThatAnswers` does. This is what "at the default effort" means in Done when: what a new chat sends. The other live tests stay on `model: nil`.
3. **The follow-up asks about the other half.** Turn 1: "What color is the left half of the attached image? One word." Turn 2, after the file is deleted: "What color is the right half of that image? One word." Turn 2 then has to read the image, not the first answer. Keeping today's prompts with only the size change also passed 4 of 4; pick that if you want the smaller diff.

## Review Focus

1. A real screenshot at low effort is not covered by any test. The probes only show that a 512x512 two-color image reads right. If you see wrong screenshot answers in the app, file an issue; this ticket does not cover it.
2. A one-word answer that names both colors ("red and blue") must fail. The checks below test that the other color is absent.
3. In 1 of 13 probe runs the low-effort turn ran shell commands to decode the PNG (read-only sandbox, no approval asked). The test uses `run`, which declines any approval, so a command that asks cannot leave the test waiting.

```swift
let client = CodexClient(defaults: freshDefaults("pauri-live-image"))
try await client.start()
let choice = try #require(ModelChoice.menu(try #require(client.models)).first)
let file = FileManager.default.temporaryDirectory.appending(path: "pauri-live-\(UUID()).png")

let right = try await run(client, "What color is the right half of that image? One word.", model: choice).text.lowercased()
#expect(right.contains("blue") && !right.contains("red"))
try await quit(client)
```
