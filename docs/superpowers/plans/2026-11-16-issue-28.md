# Sparkle and the Header Update Button Implementation Plan (refs #28)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Pauri checks for a new version in the background with Sparkle. When one is out, an up-arrow-in-a-circle button shows in the panel header, and one click downloads it, swaps the app, and restarts Pauri. No Sparkle window or alert ever shows.

**Architecture:** Sparkle 2 is a Swift package dependency. `scripts/build-app.sh` copies `Sparkle.framework` into `Contents/Frameworks`, adds the rpath, and signs the framework's parts inside-out before the app. A new `Updater` class is Sparkle's *user driver* (it gets every "show the user X" call and shows nothing) and its *updater delegate* (it names the feed). It holds Sparkle's "install?" reply until the user clicks the header button. The updater starts only when a feed is set: a release build (Info.plist key `PauriChecksForUpdates`, set by #29's release script) or the test hook (user default `PauriTestFeedURL`). A dev build has neither, so it never checks.

**Tech Stack:** Swift 6, SwiftUI, Sparkle 2.10.1 (SwiftPM binary target), POSIX `sh`, `ditto`, `install_name_tool`, `codesign`. Sparkle's `generate_keys` and `generate_appcast` tools for the owner's steps and the hand check.

**Spec:** issue #28. Decisions 5, 6, 7, 11, and 12 of #26.

## Proven before planning (scratch package, 2026-11-16)

Run in a throwaway SwiftPM package in the planning session's scratch folder. Nothing in the repo or the keychain changed.

- `.package(url: "https://github.com/sparkle-project/Sparkle", from: "2.10.1")` resolves to 2.10.1 (the latest 2.x tag) with Command Line Tools only. The first `swift build` downloads the framework zip and took about 3 minutes.
- `swift build -c release` puts `Sparkle.framework` next to the binary in `--show-bin-path`. The binary's rpaths are `/usr/lib/swift`, `@loader_path`, and the toolchain's folder, and it loads `@rpath/Sparkle.framework/Versions/B/Sparkle`. So inside an app bundle it needs `install_name_tool -add_rpath @executable_path/../Frameworks`.
- The tools are in `.build/artifacts/sparkle/Sparkle/bin/`: `generate_keys`, `generate_appcast`, `sign_update`, `BinaryDelta`.
- A bundle made with `ditto` of the framework into `Contents/Frameworks`, `rm -rf` of `Versions/B/XPCServices` and the `XPCServices` link, `-add_rpath`, then `codesign --force --sign -` on `Versions/B/Autoupdate`, `Versions/B/Updater.app`, the framework, and the app, in that order, passes `codesign --verify --strict --deep` and its binary runs and loads Sparkle.
- In Swift 6 mode, a `@MainActor @Observable final class` that is `NSObject, SPUUserDriver, SPUUpdaterDelegate` compiles with no warning. Sparkle marks both protocols and `SPUUpdater` `NS_SWIFT_UI_ACTOR`. The Swift names are in Task 2.
- Sparkle's own test app uses the feed `http://localhost:1337/...` with no App Transport Security exception. Apple's ATS page says macOS 14 blocks plain-http connections to IP addresses but not to unqualified names, so the test feed uses `localhost`, not `127.0.0.1`.
- At planning time the login keychain has no Sparkle key and `security find-identity -p codesigning` lists no `Pauri Self-Signed` identity (from this session's view).

### Gate 1 decisions

- **Hiding Sparkle's UI: both a custom user driver and settings.** `Updater` is the user driver, so no Sparkle window can exist: every "show" call either stores a reply, answers it at once, or does nothing. `SUEnableAutomaticChecks = YES` in Info.plist also skips the first-launch permission question; the driver answers that question "yes, check; no system profile" in case it comes anyway.
- **A click downloads, then installs.** No silent background download (`SUAutomaticallyUpdate` stays unset). This is #26 decision 5 word for word ("One click downloads it, swaps the app, and restarts Pauri"), and it means no update ever installs on quit without a click. While the download runs, the button shows a small spinner and cannot be clicked again.
- **A click while an answer streams: it cannot happen.** The button is disabled while `!chat.canStartNewChat` (an answer, a handoff draft, a chat opening, or the app-server starting), the same rule as the new-chat button. Its tooltip then says `Update after the answer ends`. A restart in the middle of an answer would cut the answer off; waiting with a queued click would restart Pauri at a moment the user did not pick.
- **Dev build vs release build: one Info.plist key.** The updater starts only if Info.plist has `PauriChecksForUpdates = YES` (absent from `Support/Info.plist`; #29's release script sets it before signing) or the user default `PauriTestFeedURL` is set. The test feed wins over the release feed.
- **Button place: just left of the `⌘K` hint**, so the `⌘K` hint stays next to its search button. Same font size and `.borderless` style as the gear, no tint.
- **Sparkle's XPC services are deleted from the bundle.** Pauri is not sandboxed, so they go unused (Sparkle's sandboxing page), and three fewer parts need signing.
- **The key uses Sparkle's default keychain account (`ed25519`).** `generate_keys` reuses a key that is already there, and Sparkle says one key can serve many apps. #29's release script then needs no `--account` flag.
- **The owner makes the key at gate 2, not before the build.** Dev builds never start the updater, so Tasks 1 and 2 build and test without a key. The builder stops at gate 2 with the owner's steps; Task 3 adds the public half and runs the hand check after the owner replies.
- **`Package.resolved` is committed**, so every build uses Sparkle 2.10.1 until someone runs `swift package update`.

## Review Focus

1. **A click while an answer streams.** Expected: the button is greyed out and its tooltip says to wait; after the answer ends, one click updates. Covered by hand-check step H6.
2. **The download fails after the click** (feed server down, no network). Expected: no Sparkle alert, Pauri keeps running, the spinner goes away and the button goes away until the next check (Sparkle's default: once every 24 hours, or at the next launch). Covered by hand-check step H5.
3. **Pauri is relaunched by Sparkle.** Expected: exactly one `codex app-server` runs afterwards, and the four macOS permissions are still granted (the update is signed with the same certificate). Covered by H7.
4. **A build signed ad-hoc** (the `Pauri Self-Signed` certificate is not in the keychain). Expected: the hand check is not valid, because each ad-hoc build has a different code identity. Task 3 Step 1 stops the hand check if the build prints `Signed ad-hoc`.
5. **A dev build with the test hook unset.** Expected: no request reaches any feed and no button shows. Covered by the unit test `devBuildNeverChecks` and by hand-check step H8 (the local server's log shows no request).

## Owner's one-time steps: the update key

Do these once, in the repo folder, after Task 1 has run (the tools come with the Sparkle package). The keychain may ask to allow access: allow it.

1. Make the key. It goes into the login keychain, and the command prints the public half:

   ```bash
   .build/artifacts/sparkle/Sparkle/bin/generate_keys
   ```

   If a Sparkle key is already in the keychain, it prints that key's public half and changes nothing.

2. Back up the private half. Export it to a file, put the file's text in the same safe place as the `Pauri Self-Signed` certificate's backup, then delete the file:

   ```bash
   .build/artifacts/sparkle/Sparkle/bin/generate_keys -x ~/Desktop/pauri-update-key.txt
   ```

   ```bash
   rm ~/Desktop/pauri-update-key.txt
   ```

3. Restore on a new Mac. Save the backed-up text to a file, import it, delete the file, then check that the public half matches `SUPublicEDKey` in `Support/Info.plist`:

   ```bash
   .build/artifacts/sparkle/Sparkle/bin/generate_keys -f ~/Desktop/pauri-update-key.txt && rm ~/Desktop/pauri-update-key.txt && .build/artifacts/sparkle/Sparkle/bin/generate_keys -p
   ```

If the private half is lost, every installed copy refuses all later updates, because Sparkle checks each update against the public half that copy shipped with. Those users then have to download Pauri again by hand.
