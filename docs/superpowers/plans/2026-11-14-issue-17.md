# Roomier Input Area, Logo-and-Effort Model Picker, Web Search Always On Implementation Plan (refs #17)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The text gets more room. The model picker shows the OpenAI Blossom, the model name, and a bar picture of the reasoning effort; a click on the bars changes the effort for the next message. The globe goes away and every thread runs with live web search. The camera leaves the main controls row and the screenshot moves to wherever the winning design puts it.

**Architecture:** Task 1 is the non-visual core, with unit tests: `ModelChoice` learns the effort levels `model/list` reports and how to step to the next one; `CodexClient` loses the web search toggle and its thread reload, and loads every thread with `web_search: "live"`; `Chat` loses `searchesWeb`. Task 2 builds the 4-variant design page and stops for the owner's pick. Task 3 ships the official Blossom SVGs in the app bundle, adds `ModelPicker.swift`, rebuilds the input area in `PanelView` to the winning variant, and updates the docs.

**Tech Stack:** Swift 6, SwiftPM, SwiftUI (macOS 14), Swift Testing. One static HTML page. No new dependency.

**Spec:** issue #17; `docs/spec.md` decisions 6, 7, 8, 14; `docs/superpowers/plans/2026-11-14-issue-4.md` (the picker and globe this ticket reworks). OpenAI design guidelines: https://openai.com/brand/ (read 2026-11-14 through the Wayback copy of 2026-11-04, because openai.com answers automated fetches with 403).

## Gate 1 decisions (owner: change any of these before go)

1. **"Every `turn/start` asks for live web search" becomes "every thread is loaded with `web_search: "live"`".** `turn/start` has no such field (probe above). `thread/start` and `thread/resume` are the only calls that load a thread a turn runs on, so the unit test checks the params of those two. The handoff fork (`thread/fork`) is left as it is: it only writes text. Alternative: none that Codex 0.169.0 offers per turn.
2. **A click on the effort bars steps to the next level and wraps** (low, medium, high, xhigh, max, ultra, then low). The tooltip names the level and its `model/list` description. This reads "clicking the effort picture changes the effort" literally. Cost: up to five clicks to get back to low, and `ultra` (automatic task delegation, the most usage) is one click past `max`. Alternative: the click opens a small menu of the levels with their descriptions.
3. **The effort picture is bars, one per level the current model reports** (six, or five on Luna), filled up to the current level. When `model/list` failed, the model has no levels and the bars are not shown.
4. **A model pick sets the effort to that entry's own level** (the Fast entry: low; the rest: their `defaultReasoningEffort`). New chat and launch reset both to the Fast entry at low, as #4 decided for the picker. The effort is not saved.
5. **The logo is the official Blossom SVG, unmodified: the black file in light appearance, the white file in dark**, drawn on its whole 716 canvas so the clear space comes with it. No tint, no wordmark. It sits on a material capsule (`.regularMaterial`) so the see-through panel never puts it straight over a busy window behind. The README gets one line that the Blossom is OpenAI's trademark and that Pauri is not affiliated with or endorsed by OpenAI. The ticket asks that "the PR links" the guidelines; this repo lands without a PR, so the link goes in the code commit body and in that README line. No written permission is asked of OpenAI; the guidelines grant use under their terms.
6. **References for the design page:** (a) Pauri's current panel: glass, the time-of-day orb, chips above the input. (b) `docs/reference/chatgpt-window.png`: text on top, controls in a row under it, all in one rounded box. (c) T3 Code's composer, where the model and effort sit under the text: send a screenshot in your reply, or swap in another reference. The variants take their feel from these, not their layout, and copy no one app.
7. **The four shapes** (Task 2 builds them only after go):
   - **A. Two-deck box.** One rounded box: the text across the full width on top, at least 2 lines, growing to 8. A deck under it inside the box: a `+` menu (Screenshot) and the picker on the left, mic and orb on the right.
   - **B. Picker strip above.** A slim strip above the input box holds the picker on the left; the chips row under it ends in a ghost "+ Screenshot" chip. The input row is the full-width text, then mic and orb.
   - **C. Side column.** The text box takes the width less a narrow column at its right, which stacks mic over orb. A quiet footer line under the box holds the picker on the left and a "Screenshot" text button on the right.
   - **D. Controls out of the input.** The input row is only the text (mic inside its trailing edge) and the orb. The picker and a screenshot button move to the panel's top bar, left of the new-chat pencil.
8. **The page goes in `design-directions/issue-17.html`** (AGENTS.md `# Visual rule`). The build stops after Task 2 for your pick; Task 3 waits for it. Mixing parts of two variants is a fine pick.
9. **#15 and #16 run at the same time.** #15 also edits `ModelListResult` and `ModelChoice` in `CodexProtocol.swift`; #16 edits the transcript part of `PanelView.swift`. Whichever lands second merges main into its branch before its last task. To keep the #15 merge small, Task 1 decodes `supportedReasoningEfforts` with the generated type's field names (`reasoningEffort`, `description`).
