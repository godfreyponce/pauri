# #31 Pauri's log lines readable in `log show`: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Pauri's five diagnostic lines show their text in `log show`, with no private data logging turned on and no user content in any line.

**Architecture:** One task. A new file declares one `os.Logger` for the subsystem `io.github.godfreyponce.pauri`. The five `NSLog` calls become calls on that logger. Every interpolated value gets `privacy: .public`. None of the values is a question, an answer, or a selection. The message text stays the same, so the `grep "first token"` and `grep "update failed"` lines in old plans still find them.

**Tech Stack:** Swift 6, `os.Logger` (macOS 11 and later; Pauri needs macOS 14).

**Spec:** Issue #31 (no comments). No design spec in `docs/superpowers/specs/`. Nothing visual, so the visual rule does not apply.

## Data flow

No data-flow change: the lines go to the same unified log as before. Only their privacy marking and their subsystem tag change.

## What is known (planning session, read-only)

- The only log calls in `Sources/` are these five `NSLog` lines (`grep -rn "NSLog\|os_log\|Logger" Sources`):
  - `Chat.swift:192`: `NSLog("Pauri: first token after %d ms", ...)`, an `Int` of milliseconds.
  - `Updater.swift:67`: `NSLog("Pauri: updater did not start: %@", "\(error)")`.
  - `Updater.swift:129`: `NSLog("Pauri: update failed: %@", "\(error)")`.
  - `HotKey.swift:106` and `HotKey.swift:143`: `NSLog("Pauri: hotkey registration failed, OSStatus %d", status)`, an `OSStatus` (`Int32`).
- **Probe run in planning (scratch binary, nothing in the repo), `/usr/bin/log show` on this Mac:**
  - `NSLog("Pauri: nslog %d", 42)` shows as `(Foundation) <private>`. This is the bug: the whole line is hidden, the integers too.
  - `Logger.notice("... \(Int32(-9878), privacy: .public)")` shows `-9878`.
  - `Logger.error("... \(String(describing: error), privacy: .public)")` shows `E(why: "feed down")`.
  - The same `String` with no `privacy:` shows `<private>`. Integers with no `privacy:` show, but this plan marks them `.public` anyway, so that every value is visibly marked.
  - `Logger.info(...)` does **not** show in a plain `log show` (it needs `--info`). So the first-token line uses `.notice`, not `.info`.
- **zsh gotcha:** in the owner's shell (zsh), `log` is a builtin. `log show ...` fails with `log:13: too many arguments`. Every hand check below uses `/usr/bin/log show`.

## Global Constraints

- No user content (questions, answers, selections) in public log lines (issue #31, Constraints).
- Do not turn on private data logging (no `Enable-Private-Data` profile, no `log config`) (issue #31, Done when).
- Subsystem string: `io.github.godfreyponce.pauri` (the `CFBundleIdentifier` in `Support/Info.plist`). Hard-code it. Do not read `Bundle.main`, because the test bundle has a different identifier.
- Keep each message's text the same as it is now, including the `Pauri: ` prefix.
- Do not change other code in the three files.

## Review Focus

1. **A Sparkle error text holds a local path with the user's account name** (for example a path in `~/Library/Caches`). Expected: it shows, because `"\(error)"` is logged public. This is gate 1 decision 1. It is not user content as the constraint defines it, but it is personal data in the log. No test, because the text comes from Sparkle.
2. **The first-token line at default level.** Expected: it shows in a plain `/usr/bin/log show` with no `--info`. Covered by hand check H1.
3. **The error lines at error level.** Expected: `log show` lists them with type `Error`. Covered by H2.
4. **A future log line with a question or an answer in it.** Expected: it stays private, because a `String` value without `privacy: .public` is private by default. No test. The rule is in the logger's doc comment.
5. **Lines printed by the tests.** `NSLog` printed to stderr during `./scripts/test.sh`, and `Logger` does not. Expected: no test reads that output (`grep -rn "NSLog\|stderr" Tests` finds nothing), so no test changes.

No new unit test: a test in the same process reads its own log lines without redaction, so it cannot prove what `log show` shows. The proof is hand check H1 and H2 on the built app.
