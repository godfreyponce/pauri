# Homebrew Tap with a Pauri Cask, and the v0.1.0 to v0.1.1 Update Proof Implementation Plan (refs #30)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `brew install --cask godfreyponce/tap/pauri` installs Pauri from the owner's own tap, each release bumps that cask, and a brew-installed v0.1.0 updates itself to v0.1.1 with one click.

**Architecture:** A new `scripts/bump-cask.sh X.Y.Z [--dry-run]` reads the sha256 of `Pauri.zip` from GitHub release `vX.Y.Z` (the asset's `digest`), clones `godfreyponce/homebrew-tap` into `build/tap/`, writes `Casks/pauri.rb` and `README.md` there from heredocs, commits `pauri X.Y.Z`, and pushes. `--dry-run` writes the files into a fresh `git init` folder instead and stops. `scripts/release.sh` checks that the tap repo exists before it builds, and calls `bump-cask.sh` after `gh release create`. The README's Install section gains the brew line. The tap's files have one source: `bump-cask.sh`.

**Tech Stack:** POSIX `sh`, `gh` 2.101 (`gh release view --json assets` gives each asset's `digest`), `git`, Homebrew 7.0.12 (`brew audit`, `brew trust`, `brew tap`).

**Spec:** issue #30. Decisions 3, 4, and 8 of #26. Builds on #29's `scripts/release.sh` (plan: `docs/superpowers/plans/2026-11-16-issue-29.md`).

## Homebrew policy, checked 2026-11-16 (Done when 1)

**Unsigned apps in Homebrew's main cask list.** Out, which is why this ticket uses a tap.

- docs.brew.sh/Acceptable-Casks, section "Platform compatibility and macOS security protections": "On macOS, apps, installers and other executable artefacts that Gatekeeper can assess must pass Homebrew's Gatekeeper checks and must not require System Integrity Protection or Gatekeeper to be disabled or bypassed."
- docs.brew.sh/Cask-Cookbook: "Official macOS casks must also meet the Gatekeeper requirement".
- brew.sh/2025/11/12/homebrew-5.0.0/: "Casks without codesigning are deprecated" and "We will disable all Homebrew/homebrew-cask casks that fail Gatekeeper checks in September 2026." The same post: "`--no-quarantine` and `--quarantine` flags have been deprecated as Homebrew does not wish to easily provide circumvention to macOS security features." (Homebrew 7.0.12's `brew install --help` no longer lists either flag.) So a brew-installed Pauri is quarantined, and the user sees the same "Open Anyway" steps as a download.
- None of these pages applies the Gatekeeper rule to third-party taps. They speak of "Official macOS casks" and "Homebrew/homebrew-cask casks".

**Third-party taps.**

- docs.brew.sh/How-to-Create-and-Maintain-a-Tap: "we recommend that the repository's name start with `homebrew-`"; "Place any cask files you wish to make available in a `Casks` directory at the top level of your tap."; "Non-official taps require explicit trust by default."
- docs.brew.sh/Taps: "Code in a tap can run with your user's privileges." and "Tapping a repository does not grant whole-tap trust. Install a fully qualified item to trust only that item".
- docs.brew.sh/Tap-Trust, "Installing from a tap": "Installing a fully qualified formula or cask name trusts only that item:" with the example `brew install --cask user/repository/cask`. Also: "Commands that need to load an untrusted tap or item will fail until the relevant trust is granted".

So the README's one line, `brew install --cask godfreyponce/tap/pauri`, taps, trusts the one cask, and installs. No `brew trust` step is needed for users.

**Cask stanzas** (docs.brew.sh/Cask-Cookbook): `auto_updates true` "Asserts that the cask artifacts auto-update."; `depends_on arch: :arm64`; "Top-level `depends_on macos:` marks a cask as macOS-only and declares the minimum compatible macOS release", with the example `depends_on macos: :monterey`. So macOS 14 or later is `depends_on macos: :sonoma`, not the older `">= :sonoma"` form.


  If the owner says go without this, the build proves only the stops in Task 1, and every proof that needs v0.1.0 moves to the owner's gate 2 steps.
- **`bump-cask.sh` writes the whole tap each time** (the cask and the tap's README), from heredocs in the script. The tap has one source, and its history shows only the version and sha256 lines changing per release. The cost: a hand edit in the tap is overwritten at the next release. The tap's README says so. The other choice is `sed` on a cask that already exists; that needs the first cask written by hand.
- **A separate `bump-cask.sh`, not more lines inside `release.sh`.** `release.sh` cannot run twice for one version (the tag exists after the first run). If the tap push fails after the release is out, the owner reruns `scripts/bump-cask.sh X.Y.Z` alone. The same script writes v0.1.0's first cask at gate 2, before the new `release.sh` is on main.
- **The sha256 comes from GitHub's `digest` for `Pauri.zip`,** not from the local zip. It is the hash of the file users download.
- **The issue stays open after the accept push, until the owner's v0.1.1 proof.** `release.sh 0.1.1` needs this ticket's code on `origin/main`, so the update proof can only run after the push. The accept-time docs commit says the proof is pending; `gh issue close 30 --comment` carries its result. The other choice is a second, small docs commit after the proof.

5. **A manual `bump-cask.sh` with an older version** would point the cask back at an older release. No guard: only the owner runs it, and `release.sh` already refuses a version that is not newer. Named, not tested.
