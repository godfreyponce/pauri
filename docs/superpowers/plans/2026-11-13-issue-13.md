# Codex Stdout Reader Without a Shared Blocking Read Implementation Plan (refs #13)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Two `CodexClient`s with live app-servers in one process both answer, because each one reads its app-server's stdout on its own, not through `FileHandle.bytes`.

**Architecture:** `FileHandle.bytes` reads every handle in the process one at a time, so a reader on an idle pipe blocks every other reader (probe below). Pauri reads stdout with `FileHandle.readabilityHandler` instead: each handle gets its own dispatch source, which hands over chunks of `Data` only when there is something to read. The chunks go into an `AsyncStream<Data>`, and `forEachLine` splits that stream into lines on "\n" only, as it does today.

**Tech Stack:** Swift 6, Foundation, Swift Testing. No new dependency.

**Spec:** issue #13. No design spec. Builds on #2 (one warm app-server per client) and #3 (the live tests and their `quit` workaround), `docs/superpowers/plans/2026-11-13-issue-3.md`.

## Data flow

No data-flow change: Pauri still reads the same `codex app-server` stdout pipe and writes the same stdin pipe; only how the read waits for bytes changes, inside `CodexClient.spawn`.

## What the probe found (2026-11-13, Swift 6.2.1, this Mac, 12 CPUs)

The planning session ran two probes in its scratchpad. No codex was involved.

- **Red.** Reader A runs `for try await _ in idle.fileHandleForReading.bytes` on a pipe nobody writes to. Then one line goes into a second pipe, and reader B reads it with `.bytes`. B gets nothing in 3 s: `bytes: B STALLED for 3 s`. With 12 CPUs one blocked thread cannot use up the concurrency pool, so the cause is not "a cooperative thread is blocked" as the #3 sample suggested. The `.bytes` reads of all handles wait on each other.
- **Green.** The same probe with a `readabilityHandler` reader on each pipe: `handler: B got its line after 0.000126375 seconds`.
- The planned `chunks(of:)` and chunk-based `forEachLine` (Task 1, Step 3) compile with `-swift-version 6`. They give `["a\u{2028}b", "cd", "e"]` for a pipe written as `"a\u{2028}b\nc"`, then 50 ms later `"d\ne\n"`. They give `["{\"a\":1}", "{\"b\":2}", ""]` for the handmade chunks `{"a":`, `1}\n{"b"`, `:2}\n\n`, `tail`. An idle reader ends when its pipe's write end closes.

The red probe, to rerun it (`swiftc -o probe probe.swift && ./probe`):

```swift
import Foundation
let idle = Pipe(), busy = Pipe()
Task.detached { for try await _ in idle.fileHandleForReading.bytes {} }
try await Task.sleep(for: .milliseconds(200))
try busy.fileHandleForWriting.write(contentsOf: Data("hello\n".utf8))
Task.detached { for try await b in busy.fileHandleForReading.bytes where b == 10 { print("B got its line"); exit(0) } }
try await Task.sleep(for: .seconds(3))
print("B STALLED for 3 s"); exit(1)
```

## Gate 1 decisions (owner: change any of these before go)

1. **`readabilityHandler`, not a thread per reader.** Each pipe gets its own dispatch source and costs no thread while it waits. A dedicated `Thread` with a blocking `availableData` loop also works, but it keeps one thread per app-server blocked for its whole life.
2. **`forEachLine` takes `AsyncStream<Data>` chunks, not bytes.** It splits each chunk on "\n" and joins a line that spans two chunks. The other choice keeps the byte signature and flattens chunks into bytes, which means one `AsyncStream` yield per byte for no gain. The U+2028 rule does not change.
3. **A new non-live test with two pipes, one idle.** It runs in every `./scripts/test.sh`, so the normal suite shows the stall is gone. The live test the ticket asks for runs only with `PAURI_LIVE=1`. Its limit: it calls `chunks(of:)` directly, so it does not catch a later change that puts `.bytes` back into `spawn`. And if a regression ever makes it stall, it hangs rather than fails.
4. **`quit` stays, with a new reason.** In `liveFollowUpSurvivesRelaunch` and `liveChatShowsOldTurnsAfterAFailedStart` it stands for quitting Pauri before a relaunch that shares the saved thread id. At the end of each test it makes sure the test leaves no app-server running. `.serialized` goes.
5. **No red run of the live test.** Before the fix, the new live test hangs in `second.start()` with no error, and the build session cannot wait on a hang. The probe above is the red evidence.

## Global Constraints

- Keep the one warm app-server per client from #2.
- Keep splitting lines on "\n" only (`forEachLine`): Codex writes U+2028 raw inside JSON strings.
- Swift 6 language mode (`swift-tools-version:6.0`), macOS 14.
- Public repo: no env values, credentials, or owner personal data in code, tests, or commits.

## Review Focus

1. **Restart with an old reader that never reaches end-of-file** (the `codex` wrapper dies, a child keeps the pipe open). The new client's reader must still get its replies. Covered by `idlePipeDoesNotStallAnotherReader`: the idle pipe stands for the old one.
2. **One JSON line longer than one chunk** (a `thread/resume` reply with a long chat can pass the 64 KB pipe buffer). The line must arrive whole. Covered by `linesJoinAcrossChunks`.
3. **U+2028 / U+0085 inside a JSON string.** Must not split. Covered by the kept `linesSplitOnlyOnNewline`, now read through `chunks(of:)`.
4. **The app-server exits.** The handler gets empty `Data`, removes itself, and finishes the stream, so the reader task ends. `processEnded` still does the reset, as today. Covered by `idlePipeDoesNotStallAnotherReader` (its idle reader ends at end-of-file).
5. **Bytes after the last "\n" at end-of-file** are dropped, as today. Codex ends every message with "\n". No new test.

/// A reply can pass the pipe buffer and arrive in two chunks; two lines can share one chunk.
@Test func linesJoinAcrossChunks() async {
    let split = AsyncStream<Data> { continuation in
        for part in ["{\"a\":", "1}\n{\"b\"", ":2}\n"] { continuation.yield(Data(part.utf8)) }
        continuation.finish()
    }
    var lines: [Data] = []
    await forEachLine(in: split) { lines.append($0) }
    #expect(lines == [Data("{\"a\":1}".utf8), Data("{\"b\":2}".utf8)])

/// An app-server that never writes again (#13) must not keep another one's replies from arriving.
@Test func idlePipeDoesNotStallAnotherReader() async throws {
    let idle = Pipe()
    let idleReader = Task { await forEachLine(in: chunks(of: idle.fileHandleForReading)) { _ in } }
    let busy = Pipe()
    try busy.fileHandleForWriting.write(contentsOf: Data("{}\n".utf8))
    try busy.fileHandleForWriting.close()

    var lines: [Data] = []
    await forEachLine(in: chunks(of: busy.fileHandleForReading)) { lines.append($0) }
    #expect(lines == [Data("{}".utf8)])

    try idle.fileHandleForWriting.close()
    await idleReader.value
}

- [ ] **Step 3: Implement `chunks(of:)` and the chunk-based `forEachLine` in `Sources/Pauri/CodexClient.swift`**

`chunks(of:)` sets `handle.readabilityHandler`. In it: read `availableData`; when it is empty (end-of-file), set the handler to `nil` and finish the stream; otherwise yield the data. Its doc comment says why it exists: `FileHandle.bytes` reads every handle in the process one at a time, so an idle app-server stalls another one's reader (#13).

`forEachLine` keeps its doc comment and its "\n"-only rule. The splitting, as the probe ran it:

```swift
var line = Data()
for await chunk in chunks {
    var rest = chunk[...]
    while let newline = rest.firstIndex(of: UInt8(ascii: "\n")) {
        line.append(rest[..<newline])
        await body(line)
        line = Data()
        rest = rest[rest.index(after: newline)...]
    }
    line.append(rest)
}
```

In `spawn`, the detached reader becomes `await forEachLine(in: chunks(of: reading)) { ... }`. Drop the `try?`; the body does not change.
