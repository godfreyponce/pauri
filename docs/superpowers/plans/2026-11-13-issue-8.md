# Context-Full Banner and Handoff Implementation Plan (refs #8)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** When a chat gets long, a banner says so and offers "Write a handoff draft" (a new chat with a Codex-written summary of the old one in the input box, never sent on its own) and "New chat" (same as Cmd+N).

**Architecture:** Codex already reports, after every turn and right after `thread/resume`, how many tokens the thread's last request held and the model's context window (`thread/tokenUsage/updated`). `CodexClient` passes that to `Chat` for the current thread only. `ContextLimit.isFull` compares it with one named guess (70%), or with a tiny debug value when a hidden `UserDefaults` key is on. The handoff draft comes from an ephemeral fork of the thread (`thread/fork`, `ephemeral: true`): Codex reads the whole chat on the fork and writes the note, so the old chat on disk gets no extra turn.

**Tech Stack:** Swift 6, SwiftUI, AppKit, Foundation, Swift Testing. No new dependency.

**Spec:** `docs/spec.md` decision 12; issue #8. Builds on #3's plan, `docs/superpowers/plans/2026-11-13-issue-3.md`.

## Data flow

```text

   |
   +-- thread/tokenUsage/updated {threadId, tokenUsage.last.totalTokens, modelContextWindow}
   |   (new: Pauri starts reading it; sent after each turn, and right after thread/resume)
   v
CodexProtocol.swift: CodexNotification.contextUsage(threadID:, ContextUsage) (new)
   |
   v
CodexClient (changed) --onContextUsage, current thread only (new)--> Chat.contextUsage (new)
                                                                        |
UserDefaults io.github.godfreyponce.pauri, key contextBannerDebug (new)--+--> ContextLimit.isFull (new)
                                                                        |
                                                                        v
                                                     PanelView: context banner (new)
                                                        |                        |
                                          "Write a handoff draft"           "New chat"
                                                        |                        |
                                                        v                        v
                         CodexClient.writeHandoff() (new)                 Chat.newChat() (as Cmd+N)
                           thread/fork {threadId, ephemeral: true} (new)
                           turn/start on the fork, handoffPrompt (new)
                           --> codex app-server; the fork is never written to ~/.codex/sessions

                                                           to several lines); sent only on Return
```

## What the probe found (2026-11-13, codex-cli 0.167.2, model gpt-6.1-sol, this Mac)

A Python probe in the planning session's scratchpad drove the real server.

- After each turn Codex sends `thread/tokenUsage/updated`:
  `{"threadId":..., "turnId":..., "tokenUsage": {"total": {...}, "last": {"totalTokens": 18006, "inputTokens": 18001, ...}, "modelContextWindow": 475000}}`.
  `last` is the last request: what the context holds now. `total` adds up every request in the
  thread, so it grows much faster than the context (34,249 vs 18,006 after two tiny turns).
- One short question ("what is 2+2") already holds 16,243 tokens of 475,000 (3.4%): Codex's own
  instructions and tools. Each tiny turn after it adds about 1,800.
- `modelContextWindow` is typed `number | null`.
- `thread/fork` with `{threadId, ephemeral: true, excludeTurns: true, cwd, sandbox, approvalPolicy}`
  returns `result.thread.id` (a new id), `thread.ephemeral: true`, `thread.path: null`. A turn on
  the fork ("Write a short handoff note ...") answered from the whole chat in 4.5 s: "We calculated
  2 + 2 = 4, then multiplied the result by 3 to get 12. No pending tasks." Its usage notification
  carries the **fork's** id. The original thread then took a third turn as normal, and
  `thread/resume` on a new process showed 3 turns: the fork added nothing. Resuming the fork's id
  fails ("no rollout found"): it was never saved.
- `thread/resume` on a new process is followed, after its reply, by `thread/tokenUsage/updated`
  for the resumed thread, with the same numbers as its last turn. So a relaunch can show the
  banner before any new question.
- Codex has its own auto-compaction (`model_auto_compact_token_limit` in its config, null by
  default here). Its default trigger point for this model was not found. If Codex compacts below
  70%, `last.totalTokens` drops after the compaction and the banner never shows: see Review Focus 3.

## Gate 1 decisions (owner: change any of these before go)

1. **Measure `last.totalTokens` against `modelContextWindow`.** That is how full the context is
   now. `total` is the running sum of every request and would trip the banner far too early. A
   `null` window means no banner.
2. **The threshold is `ContextLimit.guess = 0.7`, labeled a guess in the code.** No receipt: it
   is not measured. It means 332,500 tokens on gpt-6.1-sol. Tune it by changing that one value.
3. **Codex writes the handoff note on an ephemeral fork.** The old chat stays as it was, and the
   note costs one turn that reads the whole chat. Alternatives: (a) ask on the old thread itself,
   which adds a turn to the old chat and shows it there on reopen; (b) no model: paste the old
   questions and answers into the box, which is free and instant but is a transcript, not a
   summary, and is long exactly when the chat is full.
4. **The debug setting is a hidden `UserDefaults` key, not a row in Settings:**
   `defaults write io.github.godfreyponce.pauri contextBannerDebug -bool YES`. It lowers the
   threshold to `ContextLimit.debugThreshold = 0.01`, which every chat passes after its first
   answer (the probe's one short question is 3.4%). Alternative: a "Show the context banner early"
   toggle in the gear popover, which every user of the public app would see.
5. **Visual rule applies: four banner variants first.** References, proposed: (a)
   `docs/reference/retirement-banner.png`, the ChatGPT banner the spec names as the simplicity
   target; (b) Pauri's own panel as it is now (`open build/Pauri.app`). Owner: confirm or name
   others. The builder makes `design-directions/issue-8.html`, then stops for the pick.
6. **The banner has no close button.** It stays until the chat changes: a handoff or a new chat.
7. **Banner copy:** "This chat is getting long. Codex may start to lose track of earlier parts."
   Buttons: "Write a handoff draft", "New chat". While the note is written, the first button reads
   "Writing draft..." with a small spinner, and both buttons, Cmd+N, and Return are off.
8. **The input box grows to several lines** (`axis: .vertical`, `lineLimit(1...8)`; 8 is a guess:
   enough to read a note without hiding the chat). A one-line box cannot show a note to edit. The
   handoff note replaces whatever was typed in the box. #10 (the send orb) also changes the input
   bar; this ticket keeps its change to the text field only.

The handoff prompt, also changeable here, is `CodexClient.handoffPrompt`:
"Write a handoff note that lets a new chat continue where this one leaves off. Say what we are working on, what is decided, and what is still open. Write it to the assistant of the new chat, in plain text, with no preamble."

## Global Constraints

- The handoff draft is never sent on its own (issue #8 constraint). Only the user's Return sends it.
- Keep the one warm `codex app-server` process. The fork runs on it; nothing spawns a second one.
- The fork overrides match `thread/start`: `"cwd": <home>`, `"sandbox": "read-only"`, `"approvalPolicy": "never"`, plus `"ephemeral": true`, `"excludeTurns": true`.
- The fork's id is never saved under `lastThreadID`.
- `UserDefaults` key: `contextBannerDebug` (a `Bool`). Bundle id: `io.github.godfreyponce.pauri`.
- No new dependency.
- Public repo: no env values, credentials, emails, or owner personal data in commits or test fixtures.
- Commit form, from AGENTS.md `# Commit format`: `type(scope): summary (refs #8)`. Trailers: the harness default `Co-Authored-By` line, nothing else.
- Multi-task plan: one commit per task on branch `issue-8`. STATE.md is not touched in this build.

## Review Focus

1. **The handoff fails** (Codex dies, or the fork turn fails, for example a context that is already over the window): the notice shows the error, the old chat and the banner stay, and nothing is in the box. `Chat.writeHandoff` returns `nil` and calls `newChat()` only on success. Manual check 6.
2. **A full chat reopened after a relaunch** shows the banner before any new question, from the usage Codex sends after `thread/resume`. `launch()` sets `threadID = saved` before it sends `thread/resume`; set after the reply, the usage line that follows can arrive first and be dropped as another thread's. Live test, manual check 5.
3. **Codex compacts the chat:** `last.totalTokens` drops and the banner goes away until the chat fills again. Accepted; no code for it.
4. **The fork's own usage** (same size as the full chat, different thread id) must not reach the banner, or the new chat after a handoff would open with the banner already up. `CodexClient` passes usage only when `threadId == threadID`. Live test.
5. **Cmd+N, the pencil, "New chat", or Return while the note is written:** nothing happens. `isWritingHandoff` is in `canStartNewChat` and in `send`'s guard. Manual check 3.
