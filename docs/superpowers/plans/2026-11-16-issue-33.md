# Installed 0.1.0 Shows No Update Button Implementation Plan (refs #33)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Name why the installed 0.1.0 found no update, prove it with a red command, and get the owner's one-click update from 0.1.0 to 0.1.1 to pass.

**Architecture:** Pauri and Sparkle are not at fault. At 23:26:44 UTC, 63 seconds after `gh release create v0.1.1`, GitHub's `releases/latest/download/appcast.xml` still redirected to the **v0.1.0** appcast. Sparkle compared 0.1.0 with 0.1.0, found nothing, and then waits 24 hours (Sparkle's default `SUScheduledCheckInterval`, 86400 s; Pauri does not set it) or a relaunch before it checks again. The feed has served 0.1.1 since then (checked 23:40 UTC). So the plan changes no app code: it records the evidence, adds one warning line to `scripts/release.sh` so the next release proof does not test inside the lag window (decision D1), and hands the owner the relaunch-and-click proof.

**Tech Stack:** POSIX `sh`, `sqlite3` and `plutil` (read Pauri's `NSURLCache` in `~/Library/Caches/io.github.godfreyponce.pauri/Cache.db`), `curl`, Sparkle 2.10.1.

**Spec:** issue #33. Builds on #28 (`docs/superpowers/plans/2026-11-16-issue-28.md`, Sparkle), #29 (`scripts/release.sh`), #30 (the update proof this ticket unblocks).

## Data flow

No data-flow change: `scripts/release.sh` only prints one more line after the release; no script, app, or service starts or stops reading or writing anything.

## Proven before planning (2026-11-16, planner session)

Each launch of the installed 0.1.0 fetched the feed (unified log, `subsystem == "com.apple.CFNetwork"`): 302, 302, 200, `finished successfully`, at 17:25:06, 17:25:13, 17:25:50, and 17:26:44 local (UTC-6). Sparkle logged no error at any of them (its log lines are public; the #28 localhost errors at 13:33 show they appear when they happen). So every check ended in "no update found", which `showUpdateNotFoundWithError` swallows.

What the last check got is still in Pauri's URL cache. The red command (Task 1) printed:

```text
      "Date" => "Mon, 16 Nov 2026 23:26:45 GMT"
      "Last-Modified" => "Mon, 16 Nov 2026 23:13:24 GMT"
            <sparkle:version>0.1.0</sparkle:version>
```

`Date` 23:26:45 is the 17:26:44 launch's response. `Last-Modified` 23:13:24 is the v0.1.0 asset (v0.1.0 release: 23:13:25; v0.1.1 asset: `Last-Modified` 23:25:40). The body lists only 0.1.0. A `curl -sL` of the same URL at 23:40:49 UTC returned the 0.1.1 appcast. The owner's own curl that "showed 0.1.1" before the relaunch likely took a different path through GitHub's caches; one good curl does not prove that every client sees the new release yet.

Ruled out: app translocation (the process runs from `/Applications/Pauri.app`), architecture (arm64 Mac, arm64 binary, feed says `arm64`), `minimumSystemVersion` (14.0 vs macOS 26.5.2), a skipped version (no `SUSkippedVersion` in defaults), a test feed (no `PauriTestFeedURL`), the installed `Info.plist` (has `PauriChecksForUpdates`, the feed URL, the key, version 0.1.0).

### Gate 1 decisions

- **D1 (pick: add the warning line).** `scripts/release.sh` prints one line after `Released ...` that says the feed can lag and when a running Pauri checks again. Alternative: no code at all, and the lesson lives only in the STATE.md gotcha written at accept. The line wins because it shows at the exact moment the next proof would go wrong. A poll loop that waits for the feed was rejected: a curl that sees the new version did not mean Pauri saw it (see above), so the wait would give false comfort.
- **D2 (pick: no app change, no README change).** 0.1.0 copies already find updates; they only checked inside the lag window. So the issue's "copies at 0.1.0 can never update themselves" case does not arise, and nobody needs `brew reinstall`. This holds only if the owner's hand check H1 passes. If H1 fails, the cause named here is wrong; the build stops (see H1).
