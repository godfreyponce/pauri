# History Palette with Search and Delete Implementation Plan (refs #22)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Cmd+K opens variant C of `design-directions/issue-21.html`: a palette over the whole panel with a search field, one row per Pauri chat (title, date, trash on hover), arrow keys, Return to open, Cmd+Delete or the trash to delete after a second press that confirms, Esc back. The header shows the chat's title, a `⌘K` hint, and a search button. Delete calls Codex's `thread/delete` and drops the ID; deleting the open chat starts a new one.

**Architecture:** Task 1 is the logic: `HistoryEntry` carries the preview and a `matches(_:)` filter, `CodexClient` gets `delete(_:)` and `forget(_:)`, and `Chat` gets `delete(_:)` and `title`. Task 2 is the look: `HistoryList.swift` becomes the palette, `PanelView` puts it in an overlay and changes the header, `EmptyState` gets the "Open your past chats" row, and the send orb waits for a reopen (carried over from #20).

**Tech Stack:** Swift 6, SwiftPM, SwiftUI (macOS 14), Swift Testing. No new dependency.

**Spec:** issue #22 and its two comments; parent #19 (decisions 4 to 9); the pick: variant C of `design-directions/issue-21.html` (CSS `.C .pal`, `.hrow`, `.search`, `rowFull`, the `.foot` key hints, and the `C` render function). Protocol types checked against `codex app-server generate-ts` from codex-cli 0.169.0: `v2/ThreadDeleteParams.ts` is `{ threadId: string }`, `v2/ThreadDeleteResponse.ts` is `{}`.

## Data flow

```text
Cmd+K / header search button (changed) / EmptyState "Open your past chats" row (new)
   --> PanelView overlay --> HistoryList palette (changed)
         --> Chat.history --> CodexClient.history --> codex app-server: thread/list
         --> search field --> HistoryEntry.matches (new), in memory only

HistoryList trash button / Cmd+Delete (new)
   --> Chat.delete (new) --> CodexClient.delete (new)
         +--> codex app-server: thread/delete (new)
         +--> UserDefaults "threadIDs": ID removed (changed: was add-only)
       if it was the open chat --> Chat.newChat --> CodexClient.forgetThread
         +--> UserDefaults "lastThreadID": removed
```

## What the probe showed (codex-cli 0.169.0, on the owner's Mac, 2026-11-15)

A throwaway script drove `codex app-server`: one thread, one turn, then `thread/delete`.

- `thread/delete` on the thread loaded in the same process returns `{}`.
- After it, `thread/list` no longer lists the thread, and `thread/resume` of it is an error (`-32600`, "no rollout found for thread id ..."). The delete is permanent.
- A second `thread/delete` of the same ID is the same error.
- `thread/list` has a `searchTerm`, but its doc says it matches "the extracted thread title" only. The ticket asks for title or text, so the filter runs in Pauri.

## Gate 1 decisions (owner: change any of these before go)

1. **Rows show the second line only when Codex named the chat.** The design row is a title, then a gray first line of the chat. Codex never names Pauri's chats (#20's probe), so the title already is the first message, and a second line would repeat it. In practice every row is one line: title, date, trash. Alternative: let the title wrap to two lines.
2. **"Delete calls `thread/delete`" is proven by a live test, not a unit test.** `CodexClient` talks to a real process and has no fake transport; adding one would be a refactor this ticket does not need. The unit test covers `forget(_:)`, the removal of the ID. The live test (`PAURI_LIVE=1`) deletes a real chat and checks Codex, the ID list, and the open chat.
3. **Delete takes a second press (owner's change at gate 1, 2026-11-15).** The first trash click or Cmd+Delete turns that row into an inline `Delete for good?` with `Delete` and `Cancel`, inside the row and in variant C's look. Only the second press (the row's `Delete` button, or Cmd+Delete again on the same row) calls `thread/delete`. Esc, moving the selection (arrows, hover on another row, or a search change that moves it), or `Cancel` drops the pending confirm. One press never deletes; the probe shows Codex deletes for good.
4. **The header title is the first line of the chat's first question, or "New chat".** No new state: it comes from `chat.exchanges`. For every Pauri chat it equals the list's title (Codex's preview), because Pauri chats have no name. A question sent with selected text starts with `> `, in the header and in the list alike.
5. **Keys are the footer's key caps, made into buttons with keyboard shortcuts.** `↑` `↓` move, `↩` opens, `⌘⌫` deletes, `esc` goes back. Shortcuts are key equivalents, which AppKit runs before the search field sees the key, so Esc drops a pending delete confirm first, then closes the palette, and never hides the panel. Cmd+K and Cmd+N already work this way in this panel.
6. **The pointer moves the selection.** Hover selects the row, so only one row is ever lit, and the trash shows on that row.
7. **The palette closes when the panel hides.** Otherwise the next hotkey would focus the hidden input under the palette.
8. **Left out: `history()` stopping early once every remembered ID is found** (#22's second comment says "could", not "fix it here"). Say so if you want it in.
9. **No new design page.** The owner picked variant C at #21's gate 1; this ticket builds it, and gate 2 compares it to that page.

@MainActor func liveDeleteDropsTheChatAndTheOpenOneStartsNew() async throws {
    let client = CodexClient(defaults: freshDefaults("pauri-live-delete"))
    let chat = Chat(client: client)
    chat.warmUp()
    try await waitUntil { !chat.isStarting }
    #expect(chat.send("what is 2+2"))
    try await waitUntil { !chat.isAnswering }
    let other = try #require(client.threadID)
    chat.newChat()
    #expect(chat.send("what is 3+3"))
    try await waitUntil { !chat.isAnswering }
    let open = try #require(client.threadID)

    #expect(client.rememberedThreadIDs == [open])

    try await chat.delete(open)
    #expect(chat.exchanges.isEmpty)

    // The process still answers after its loaded thread was deleted.
    #expect(try await answer(client, "what is 5+5").contains("10"))
    try await quit(client)
}
